PhaseSweep runs hyperparameter sweeps on this server's host. The operator owns the catalog and the experiment configs behind it: work only with the experiments `list_experiments` returns, and change a config only when the user asks for config help, starting from `explain_config`.

Each tool's description says when to call it. The loop is `list_experiments`, `inspect_experiment`, `launch_run` once the user authorizes that experiment, `await_run` with the returned `run_id` until the run is terminal, then `get_run_results`.

Stop when a response carries a `failure`, or `catalog_status.stale` is true: tell the user its `remediation` and wait. Do not retry, cancel or launch a replacement instead.

When you report a winner, include its `winner_generation` and the `represented_generation_id`, every flagged `confound` check as a flag with its counts, any `remedy` or `cost_advisory` a response carries, and an `incomplete` selection. Do not call a difference significant, and a check that reads `n/a` was not run. With `repeats`, report the metric with its `sd`, `min`, `max` and `n`. One winner per phase does not show convergence, trends, robustness, causality or what lies beyond the search range. `observed` values were recorded with a winner and did not decide it. `<redacted>` values are hidden by the catalog's policy.

These tools return winners, not trials. If you have a shell on this host and the user asks for per-trial data, read it there, with the experiment's config file as `CONFIG`: `phasesweep status CONFIG --trials` prints the trial table, `phasesweep show-winners CONFIG` the winners, and `run.log` in the `workdir` that `phasesweep status CONFIG` prints the progress. For `optuna-dashboard`, copy the `ledger_path` that command prints and open the copy, never the live ledger.
