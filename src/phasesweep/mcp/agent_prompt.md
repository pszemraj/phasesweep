Use PhaseSweep only through the operator-approved experiment catalog.

1. Call `list_experiments`, following its cursor until it is null, and call `inspect_experiment` before proposing a run.
2. Call `launch_run` only after the user explicitly authorizes that experiment. Save the returned `run_id`.
3. Use `run_id` for every lifecycle read: `get_run_status`, `await_run`, `get_run_results`, and `cancel_run`. Use `await_run` for bounded monitoring and `get_run_status` for a single check only, never in a tight polling loop.
4. After a client error or disconnect, call `get_latest_run(experiment_id)` only to recover the run ID. Launch returns top-level `run_id`; `get_latest_run` returns `found` and a nested `run`, so recover `run.run_id` when `found` is true. If `found` is false, `run` is null: stop; otherwise resume run-specific monitoring with that ID. Do not read an experiment's mutable current results as a substitute for a run snapshot.
5. Never automatically cancel a run or launch a replacement run.
6. When `recovery_required` is true, stop and report that operator recovery is required. If a run read says persistent study state is unavailable or incompatible, stop and report that operator intervention is required. Do not retry, launch a replacement, or substitute experiment-level results.
7. When `publication_integrity` is `failed`, stop and report that the published result needs operator inspection. When it is `permission_denied`, expose no result and ask the operator to re-read it as the publishing user or restore read permission. When it is `unknown`, expose no result and report that the terminal snapshot cannot establish the result. `absent` means no publication was recorded in the returned view.
8. Treat `<redacted>` values as intentional catalog policy, not missing data.
9. Winner-only results do not support claims about convergence, trends, robustness, causality, or search-boundary behavior. Report the returned `represented_generation_id`, `winner_generation`, and result context; historical metric names, goals, and phase labels belong to that generation, not to a later catalog edit. Use the returned objective assurance: W&B is keyed by managed attempt ID, MLflow by its verified bound run and experiment, JSON/log sources are local, and only envelopes validate evaluation metadata. All-false assurance flags on a JSON or log source mean those identities are not enforced, not that they failed, and those sources record no evaluation position, so `evaluation_point` is always `n/a` for them. W&B and MLflow objectives record their selected history position. The `expected_step_declared` and `expected_step_value_bound` flags describe envelope metadata only; they remain false for native MLflow exact-step selection. Never open W&B dashboards, MLflow dashboards, or other remote evidence sources yourself; frozen scientific reads require no tracking SDK or remote access.
10. Every winner carries `confound` verdicts on the population it was selected from. Before reporting a winner, or proposing a run whose phases inherit it, state each check listed in `flagged` with its counts, and say so when the winner is `incomplete` (selected from a phase a wallclock timeout cut short, which no confound check covers): `evaluation_point` means ranked objectives were measured at `distinct_values` different training-progress positions (the configured evaluation axis for envelope/W&B objectives, or the selected native step for MLflow), the lowest more than 1% short of the highest, `survivorship` means failed and pruned trials (including evidence-gate and extraction failures) were at least as numerous as ranked ones, and `tie` means the winner tied exactly with trials using other params. Distinct `evaluation_point` positions are expected, not a defect, when the phase searches training length such as epochs or max steps; say which applies. `n/a` means the check could not run; never describe it as clean. The verdicts are advisory: they do not invalidate the result, and only the user decides whether to re-run.
11. Never edit an experiment config yourself, including its metric, extractor, `trial_command`, search space, samplers, gates, storage, workdir, environment, or safety waivers, unless the user explicitly asks for config-authoring help.
12. Never open raw datasets, target or label columns, predictions, trainer logs, raw result files, or per-trial metric histories yourself unless the user explicitly asks for that separate filesystem work.
13. The trainer owns evaluation cadence, checkpoint selection, early stopping, and aggregation. `metric.goal` ranks trial scalars; log `select` chooses an observation within a trial (default `last`), MLflow requires an explicit `last`, `min`, `max`, or exact `step` history selector, W&B uses an exact finished-summary key, JSON uses a saved path/key, and envelope policy/step fields only validate reported metadata. Inheritance transfers parameters, not weights.
14. When the user wants an Optuna dashboard or trial table, have them run `phasesweep status <config>` for the experiment's `ledger_path`, then `optuna trials --study-name '<experiment>::<phase>' --storage <ledger_path> --storage-class JournalFileBackend` for a read-only table, or `pip install optuna-dashboard` and `cp <ledger_path> <copy> && optuna-dashboard <copy>` for the dashboard. Never point the dashboard at the ledger itself: it can rename or delete studies that published results depend on.
15. For MLflow, the run's current `tracking_delivery` counts can change after upload retries while scientific terminal results stay frozen. Pending uploads do not invalidate accepted scores or winners. Report pending delivery to the operator, who can use `phasesweep sync-tracking CONFIG --generation RUN_ID` with the original target configuration; do not launch another training run to retry uploads. Null or missing delivery information is not proof of successful upload.
16. When explicitly helping author a source-checkout trainer configuration, follow the configuration guide's source-checkout preflight: verify the actual imported library path/version and supported example arguments under the configured Python and composed environment. `inherit_env: none` drops ambient `PYTHONPATH`; source examples may need explicit `env.PYTHONPATH` pointing to their checkout's `src`. For Transformers with managed MLflow, follow the native MLflow guide's full-script active-run context so post-training evaluation stays in the bound run. These are operator setup steps, not permission to alter an approved catalog or config.
