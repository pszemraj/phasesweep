Use PhaseSweep only through the operator-approved experiment catalog.

1. Follow `list_experiments.next_cursor` until null, then `inspect_experiment` before proposing a run. Launch only after the user explicitly authorizes that experiment; save the returned `run_id`. Cancel only when the user explicitly asks. Never automatically cancel or launch a replacement.
2. Use `run_id` for every lifecycle read: `get_run_status`, `await_run`, `get_run_results`, and `cancel_run`. Monitor with `await_run`, which defaults to 20 seconds and accepts at most 600; request longer waits only when the client permits them. Repeat with the same ID while running, including after `reason: phase_completed`. Use status for single checks, never tight polling; read results when terminal.
3. After a disconnect or error, use `get_latest_run(experiment_id)` only to recover `run.run_id` when `found` is true. If false, `run` is null: stop. Never substitute mutable experiment results for a run snapshot.
4. When `recovery_required` is true, stop and report operator intervention. Also stop for unavailable/incompatible persistent study state or an unavailable terminal snapshot; do not retry or replace the run. When `publication_integrity` is `failed`, stop for operator inspection; for `permission_denied`, ask the operator to read as the publishing user or restore permission; for `unknown`, report that the snapshot cannot establish results. Expose no winners in these cases. `absent` means no publication was recorded in this view.
5. When `runner_observable` is false, keep monitoring durable counts with `await_run`, never call `cancel_run`, and notify the user if counts stop advancing. The server cannot establish liveness or cancel across the runner's PID namespace; [operator recovery](https://github.com/pszemraj/phasesweep/blob/main/docs/mcp.md#pid-namespaces) explains the remedy.
6. Treat `<redacted>` as deliberate policy. Report `represented_generation_id`, each `winner_generation`, and `result_context`; historical metric names, goals and phases belong to that generation. Winner-only data cannot establish convergence, trends, robustness, causality, or search-boundary behavior.
7. Before reporting a winner or proposing phases that inherit it, report every `confound.flagged` check with its counts and any `incomplete` selection. `n/a` is unchecked, never clean. Distinct evaluation positions are expected when searching training length; a `json_envelope` metric with `evaluation_axis: schedule_fraction` compares relative schedule completion instead and still flags a run that stopped early ([training-length comparison](https://github.com/pszemraj/phasesweep/blob/main/docs/config.md#training-length-comparison)). Verdicts and repeat-noise overlap are advisory, not significance tests; only the user decides whether to re-run. `observed` values are report-only. With non-null `repeats`, report the reduced `metric` with `sd`, `min`, `max`, and `n`; observations are means over members that recorded them. See [confound verdicts](https://github.com/pszemraj/phasesweep/blob/main/docs/runtime.md#confound-verdicts) and [repeat groups](https://github.com/pszemraj/phasesweep/blob/main/docs/runtime.md#repeat-groups).
8. Interpret returned objective assurance without inventing guarantees: W&B binds the managed attempt; MLflow binds its verified run and experiment; only envelopes validate evaluation metadata. All-false JSON/log flags mean identities are unenforced, not failed, and their `evaluation_point` is always `n/a`. W&B/MLflow record selected history positions; `expected_step_declared` and `expected_step_value_bound` describe envelopes and remain false for native MLflow exact-step selection. The trainer owns evaluation and aggregation; `metric.goal` ranks trial scalars, and inheritance transfers parameters, not weights. See [objective evidence](https://github.com/pszemraj/phasesweep/blob/main/docs/config.md#objective-evidence-constraints-and-gates).
9. Never open W&B dashboards, MLflow dashboards, or other remote evidence sources yourself; frozen scientific reads need no tracking SDK or remote access. Never open raw datasets, target/label columns, predictions, trainer logs (including `run.log`), raw results or per-trial histories without explicit authorization for that separate filesystem work. Direct users seeking trial tables, logs or dashboards to [operator inspection](https://github.com/pszemraj/phasesweep/blob/main/docs/runtime.md#inspection-commands), [progress](https://github.com/pszemraj/phasesweep/blob/main/docs/runtime.md#following-a-run), and [Optuna inspection](https://github.com/pszemraj/phasesweep/blob/main/docs/runtime.md#inspect-the-ledger-with-optuna). For trial tables, ask the operator to run `phasesweep status CONFIG --trials`; for progress, `tail -f run.log` in the experiment output directory. For a dashboard, obtain `ledger_path` with `phasesweep status CONFIG`, install `optuna-dashboard`, and run `cp LEDGER COPY && optuna-dashboard COPY`. Never point a dashboard at the live ledger: it can rename or delete studies.
10. Report pending MLflow `tracking_delivery` to the operator; missing/null counts do not prove delivery. Counts can change while scientific results stay frozen. The operator can retry with `phasesweep sync-tracking CONFIG --generation RUN_ID` using the original target config; never retrain for delivery. See [delivery recovery](https://github.com/pszemraj/phasesweep/blob/main/docs/mlflow.md#result-delivery-and-recovery).
11. Never edit an experiment config yourself unless explicitly asked for config-authoring help. Then call `explain_config` for relevant keys (omit the key for top-level keys and general notes). For source-checkout trainers, verify the imported library path/version and supported arguments under the configured environment. Default `inherit_env: none` drops ambient `PYTHONPATH`; configure `env.PYTHONPATH` when the trainer needs it; see [preflight](https://github.com/pszemraj/phasesweep/blob/main/docs/config.md#source-checkout-preflight). For Transformers with managed MLflow, keep the full script in its bound active-run context; see [integration](https://github.com/pszemraj/phasesweep/blob/main/docs/mlflow.md#transformers-trainer). Use `phasesweep init --list` and `phasesweep init --template NAME` to choose and write [templates](https://github.com/pszemraj/phasesweep/blob/main/docs/config.md#templates) as starting points. Prefer more distinct continuous values before `repeats`; propose repeats for discrete finalists near the noise or when requested. See [noisy objectives](https://github.com/pszemraj/phasesweep/blob/main/docs/config.md#noisy-objectives-and-small-budgets).
