# Durability invariants

The experiment lock serializes local ledger mutations. Artifact-root and format checks precede claims, durable outcome records precede terminal trial states, and generation validation precedes the publication-pointer commit. No trial or detached-runner code runs before its process identity is durable, and operator recovery identifies processes from durable attempt and run records.

## Invariants

Module paths below drop the `phasesweep.` prefix; test paths are relative to the repository root.

### Lock and ledger order

`engine.ledger` alone constructs Optuna storage. Its configured-ledger handles prove the preceding checks ran. `open_registry_study` instead validates and repairs the ledger named by a registered attempt. [Development](development.md#quality-gates) describes the contract checks.

    recover["recover-run"] -->|"confirmed"| lock
    recover -->|"inspection, holds no lock"| check
    reads["status, show-winners, MCP reads"] -->|"holds no lock"| check
    lock --> check
    subgraph validate["validate_ledger: writes nothing"]

        rescan["strict rescan if the scan did not complete"] --> repair["cut a partial final journal record<br/>under the PhaseSweep inode lock"]

#### 1. Mutations hold the experiment lock

Runs, confirmed `recover-run`, and `sync-tracking` hold the same experiment lock before writes and the reads they depend on. Fresh-tree run checks are the exception ([invariant 11](#11-only-work-claims-a-generation-after-every-check-that-could-refuse-it)). `sync-tracking` validates the binding and format before retiring tracking attempts or writing the tracking tree, and reads trials through that validated handle.

The status lock probe controls resume advice only. Both status formats retain trial data and the publication verdict when the probe fails. On macOS, root-owned `/var` and `/tmp` aliases share the physical path's host locks. Operator-controlled symlinks are refused. See [storage and locks](runtime.md#storage-and-locks) for lock path requirements.

**Held by:** `cli._status_can_suggest_resume`, `runtime.files.lock_dir`, `engine.locking._experiment_lock`, entered as the outermost durable-state context in `engine.run._run_experiment_outcome`, in `mcp.recovery.recover_run` only when the operator confirms, and in `tracking.publication.sync_tracking` inside `runtime.shutdown.signal_handler_scope` for its whole body: `engine.ledger.validate_ledger` first, then tracking-only attempt resolution, record rebuilds, and deliveries

#### 2. Validation writes nothing

`validate_ledger` checks the artifact-root binding, then scans the ledger format, and writes nothing; on a bound tree an unreadable scan is tolerated and recorded on the handle, and on an unbound tree it is refused.

Readers skip an incomplete final journal record without writing. Before opening storage for mutation, claims, registry recovery, and confirmed operator recovery repair that record under the experiment lock and the journal inode lock. Repair rescans after acquiring the journal lock, saves a permission-preserving timestamped backup, truncates only the incomplete tail, fsyncs, and replays the result. A malformed record before the tail is corruption and remains unchanged.

Every PhaseSweep append and repair locks the journal inode. Writers wait without a deadline; repair waits at most 30 seconds. Kernel locks release on process exit and coordinate hard-linked names as well as resolved symlinks. Repair truncates through its locked descriptor and checks that the pathname still names that inode. Failure to acquire the lock or make the backup refuses with `RESTORE_LEDGER`. Growth or pathname replacement under the lock refuses with `RETRY`, without truncating or unlocking the replacement.

**Held by:** `engine.ledger.validate_ledger`, running `engine.artifact_roots._check_artifact_root_binding` before `engine.ledger._scan_ledger_format` and returning a `ValidatedLedger` whose `format_verified` and `format_scan_failure` record the outcome; `engine.ledger._journal_records` for the tolerated line, `engine.ledger._JournalLock` for writer and repair exclusion and `engine.ledger._repair_incomplete_journal_record` for the repair, called by `claim_ledger`, `open_registry_study`, and confirmed recovery

#### 6. Read paths construct and write nothing

`read_status`, `read_result`, `read_trial_tables`, CLI `status` (with or without `--trials`) and `show-winners`, the MCP result snapshot, `validate` when it reads recorded attempts for a fixed-configuration target above one or an above-matrix grid target, and `run --dry-run` build no file-backed storage and write no bytes. Status reads report a phase whose format scan did not complete as unavailable rather than counting its trials. A dry run reads all phase studies from one journal capture, applies the launch's claim and preflight checks in the launch's order, and renders its command on an in-memory study. [Inspection commands](runtime.md#inspection-commands) describes its refusals, limitations, and fresh preview when the ledger is unreadable.

Numeric metadata follows each consumer's error contract even when a JSON integer exceeds the float range. Publication validators reject unusable metrics, repeats and observations through publication errors; permissive winner reads omit malformed results, and optional trial-table cells become `None`. Selection excludes trials with unusable constraints, while strict resume reports a winner error. `engine.publication_validation._validate_generation_manifest`, `engine.repeats._finite_number`, `engine.state._validate_observed_block`, `engine.read._winner_view`, `engine.read._recorded_number`, `engine.selection._eligible` and `engine.artifacts._load_winner` enforce these boundaries. ### Attempts and trial outcomes

#### 8. Attempts are registered before launch

The attempt registry is scanned before anything else in the continuation preflight, and each attempt is durably registered before its trainer is launched. Each trainer entry records the producing phase and study names and an absolute storage locator, so the registry still resolves the attempt after a phase rename, a storage-URL change, or a change of working directory. Managed MLflow setup uses `tracking.session.call_tracking` for both creation and lookup. Each worker owns its lifecycle and cleanup. The trainer stays allocated until launch, so recovery retries a draw interrupted during setup or the GPU wait (`tests/test_mlflow_terminal_delivery.py::test_managed_creation_before_launch_recovers_the_unlaunched_draw`).

#### 9. Nothing runs before its process identity is durable

Trainer code and its environment execute only after the process identity is durable. The standalone stdlib supervisor starts by file path under `python -I -S` with only `PATH`. Command, environment, and cwd cross its pipe after `process_identity.json` is written; EOF before acknowledgement exits without launching the trainer.

The MCP runner starts by file path under `python -P` in the private server state directory, with Python startup-path overrides removed, so neither its script directory, the project directory nor `PYTHONPATH` reaches `sys.path` before its identity is durable; it keeps the server's user-site setting, adding `-s` exactly when the server runs with the user site disabled, so the runner imports the PhaseSweep the server imported; a W&B or MLflow worker keeps its controller's setting the same way. A durable handle is created before `Popen`, replaced by the runner's receipt after it persists its process identity, and confirmed through a ready/ack handshake. The receipt requires a boot id and PID namespace. The runner receives the project path as `--cwd`, entering it only after its receipt is persisted and the handshake completes. Its durable handle reserves the run across server restarts, preventing a duplicate launch.

#### 10. Lifecycle states that skip signalling are written only on proof

A durable lifecycle state authorizes recovery to skip process-identity cleanup only when it proves no process can remain. `allocated` is written before registration, trial discovery and GPU waiting, so without a process identity beside it, no launch began. `launching` precedes `Popen`, and the trial-directory attribute precedes `launch_trial`, so an undiscovered trial cannot hide a launch. The payload crosses only after `process_identity.json` is written, so `launching` with no identity file beside it means no worker received its payload: recovery acts on it only under the experiment lock, which proves the controller that held the payload pipe is dead, and a supervisor that reads end-of-file instead of a payload exits without running the trainer. Recovery therefore settles that attempt without signalling and without writing `exited`; a trainer that had already finished keeps its recorded result, and a trainer attempt records `interrupted` and reruns. An identity file that exists at all, even empty, partial or another attempt's, still requires identity validation. `exited` with confirmed cleanup is written only once the whole group and every descendant the guardian adopted are proven gone or no supervisor was spawned; `process_identity.json` stays beside it. That is the guardian's guarantee: recovery of an attempt whose controller was killed confirms only the recorded process group, so `engine.attempts._resolve_attempt` can write `exited` while a guardian still alive holds an adopted helper that left the group. Every other state requires identity validation.

Cleanup requires proof that every member has exited. On Linux the guardian is a child subreaper, so the members are the trainer group's processes and the guardian's own children: the root and every descendant whose parent died first, such as a rank torchrun started in a session of its own. The group is checked first; then `waitpid(-1, WNOHANG)` reaps every exited child and says whether any is left, and procfs only lists the adopted children's PIDs so they can be named and signalled. That order is race-free: a group with no live member gains none, and the kernel re-parents a dying process's children to the guardian before that process reads as exited. While the root runs, the guardian's wait reaps each adopted child as it exits, so none is left a zombie. SIGTERM and SIGKILL go to the trainer group and to each member's own group, and a member adopted only after its launcher was killed gets SIGKILL at first sight within the same grace. On Linux a group member has exited in procfs state `X` or in state `Z` with only its own thread listed in `/proc/<pid>/task`. Other threads can still run after the leader calls `pthread_exit`. An unreadable thread listing counts as live. The per-thread states are unnecessary because exited threads leave the listing. macOS counts zombies as exited when checking members.

A live guardian persists `terminating` with a nonzero cancellation status before forwarding shutdown, timeout or abort. That record survives a later zero exit and still requires cleanup proof. The guardian reaps the exited root during group cleanup, including without procfs. If the guardian dies, the controller takes over within the existing deadline without signalling the dead guardian's PID; it can signal only the recorded group, so a descendant outside that group re-parents to init and is no longer tracked. Supervision saves cancellation intent before directly cleaning a trainer whose guardian exited. A completed group keeps its result. Once the trainer root has exited, cancellation no longer applies: the guardian ignores it, gives the rest of the group its helper settle, then terminates and names whatever is still running, and the guardian-exit timeout and the guarded shutdown window both allow one figure: that settle plus the SIGTERM grace plus a margin for the guardian's polling and scans. A guardian unable to save intent withholds signals and retains the lease. See [interrupted trials](runtime.md#interrupted-trials-rerun) for the operator behavior.

Process-lifetime signal installation and repair register the PhaseSweep handler before unblocking shutdown signals, so queued signals cannot reach a replaced host handler. `runtime.shutdown.install_signal_handlers` and `runtime.shutdown._reassert_process_lifetime_handlers` enforce this order; `tests/test_shutdown.py::test_deferred_sigterm_exits_without_deadlocking` covers signals queued before installation, inherited masks and critical sections.

#### 12. A persistent study holds one environment cohort

A persistent study holds trials from one semantic trainer environment, as defined by the [trainer contract](config.md#trainer-contract). The config fingerprint leaves ambient values out and relies on the cohort check to prevent ranking incomparable trials together. Each trial records the tracked environment mapping and its SHA-256 digest. The digest is the first attribute written on each allocated trial, before the abort check and any lifecycle or registry write. `_run_phase` also records it on the study as an allocation context before Optuna allocates, covering a trial that dies before its first attribute. Before another allocation into a populated study, both continuation preflight and `_run_phase` refuse differing digests or a trial whose digest is neither recorded nor covered by an allocation context, and the dry run refuses the same top-up instead of previewing it. The cohort check runs first in the launch preflight, so a changed `PATH` reads as a cohort refusal that shows both values, not as a missing trial program. Per-trial `PHASESWEEP_*` and GPU bindings are applied after the digest is taken, and `CUDA_VISIBLE_DEVICES` stays out of the base inherited environment, so neither splits a cohort.

#### 13. No terminal trial without its outcome record

A durable outcome precedes every terminal Optuna state. When a persistent study cannot confirm a write of trainer exit evidence, extracted results, or the outcome, the phase leaves the trial `RUNNING` and stops new launches. After workers drain, the run reports the failed operation and its cause. Once the ledger is writable, recovery settles the attempt before allocating new work. An in-memory study has no retained trial to resume. The outcome holds the verdict, its exact finite scalar when measured, and any abort ([invariant 14](#14-an-abort-is-recorded-with-the-outcome-that-trips-it)). A rejection carries no scalar and commits as `FAIL` even if an earlier extraction wrote evidence attributes. Recovery verifies retained measurements and replays the exact scalar, including infeasible measurements. Changed or missing file evidence blocks publication until restored.

A completed trainer's exit code and duration are saved before extraction reuses its process slot. Shutdown or refusal to start an evidence worker retains the completed trainer and its registry entry for resume. An unanswered tracker read keeps persistent evidence pending unless a definite failure outranks it. A W&B settle-window failure requires an answered lookup, including a reply received during the reporting reserve. Launch stops, existing workers drain, and `TrackingTargetUnavailableError` surfaces unless unconfirmed cleanup outranks it ([invariant 16](#16-unconfirmed-cleanup-stops-new-work-until-recovery-proves-it)). Reconciliation skips a second lookup. Recovery tries once per pass and blocks new trials until evidence is available. Confirmed operator recovery settles the run and reports the pending count. In-memory trials instead fail with the tracker's reason. See [trial execution and evidence](runtime.md#trial-execution-and-evidence) for the polling and settle-window contract.

When recovering an unrecorded result, extraction uses the producing evidence source and query with the current invocation's MLflow polling controls. `engine.trial.record_trial_result` replaces optional evidence from earlier extraction, so the winner, trial table and MLflow projection omit values absent from the accepted result (`tests/test_observe.py::test_retry_replaces_optional_trial_results`). The outcome and cleanup-recovery record precede the terminal transition. Live and recovered evidence rejections write the outcome and abort before the separate diagnostic. A failure before that outcome can retry extraction. After it, a rejection survives an interrupted diagnostic. Recovery persists interruption before signalling a surviving trainer, preventing a later zero exit from establishing success. Recovery preserves a recorded failure or fatal error. Without a recorded verdict, confirmed trainer success proceeds to evidence recovery without retraining. See [interrupted trials](runtime.md#interrupted-trials-rerun) for how recovery treats other exits and interruptions.

#### 14. An abort is recorded with the outcome that trips it

The first abort after the recovery boundary is authoritative and is written with the outcome that trips it. After a write error, the completion lock prevents sequence reuse until a journal check distinguishes a matching outcome (count once), an absent outcome (retry), and unreadable or conflicting evidence (defer). Duplicate sequences make replay, recovery and preview refuse without changing either record.

In-flight peers may trip an abort while another trial awaits tracker evidence. Interrupted outcomes leave the streak unchanged, and a later success resets the streak without clearing the abort. Live and recovered outcomes use the same decision, with recovery using the producing limit and settlement order. A recovered abort blocks publication like a live one, but recovery can trip the limit at a different point if settlement order differs from trainer completion order. The current config only affects new outcomes or retires an abort under the [continuation rules](runtime.md#timeouts-cleanup-and-continuation). Unsafe cleanup requires [invariant 16](#16-unconfirmed-cleanup-stops-new-work-until-recovery-proves-it) first. Retirement records the accepted target and resets the streak in one write before new work. After an interruption that authorization survives, and only the new accepted target can continue it.

#### 18. Publication is a transaction

The generation's own summary and winners are read back and validated before `last_successful_generation.yaml` commits, a failure before the commit leaves the prior pointer authoritative, and shutdown signals are absorbed until the commit lands. Without timed signal waits, main-thread absorption keeps Python deferral active while queued kernel signals are delivered, then restores the caller's exact mask before leaving deferral; worker absorption observes pending signals without consuming them, leaving delivery to the main thread. The pointer commits before its generation's lifecycle record, so it can be the only proof that generation committed; the record is written before the pointer moves off it, and if that write fails the pointer stays. Once the pointer commits, nothing after it reclassifies the publication: each post-commit step logs and swallows its own failure, `BaseException` included, and a directory fsync after the rename never raises.

### MCP runs

#### 22. A PID alone is never authority

Process identity combines PID, start time, boot id and PID namespace. Linux uses the namespace inode and the start time of its PID 1 to survive inode reuse. macOS uses the `darwin` PID space, exact `libproc` start times and `kern.bootsessionuuid`, checks group existence with `killpg(pgid, 0)`, and reaps an exited leader only if it is this process's child. Group absence remains necessary. A reboot or host proof of foreign-namespace absence permits settlement without signals. Only the initial namespace can establish that absence across every recorded nesting level. Unreadable identity refuses cleanup. Lack of host proof for foreign-namespace processes raises `ForeignPidNamespaceError` with any blocking host process and no manual signalling advice. Numeric runner PID and PGID guidance is limited to the initial namespace. See [PID namespaces](mcp.md#pid-namespaces) and [operator recovery](mcp.md#run-state-and-recovery) for stop and inspection steps.

Registry, stale `RUNNING` and cleanup-uncertain terminal attempts all use one reaper decision. Preview reports an attempt once and lets stricter study inspection replace registry advice. Confirmation reevaluates the decision before signalling and reports a termination only when its before-termination callback ran. A matching process-birth identity or verified stored PGID after leader exit can authorize a signal. A reused group leader is spared. A manual trial check uses `pgrep -a -g` in the sweep's namespace because children can outlive the leader. A possible live runner's manual stop names its positive PID and verifies its run id by command line. For a runner proven gone, even with an unfinished snapshot, cancellation names recovery instead of a signal.

### Selection

#### 26. A confound verdict never joins a fingerprint or gets read as clean

The confound block is computed once per selection and frozen onto the winner; `n/a` means a check could not run and must never be rendered or counted as `ok`. Complete groups added by a later failed or unfinished top-up do not join an earlier winner's comparison. Its cost window uses the winner's standard error; equal costs prefer the better objective, then trial order. MCP redacts its parameter-bearing text under the winner visibility policy.

A repeat group holds exactly one trial per repeat value: under grid its key is the trial's params without the repeat key, and under seeded random it is also the configuration slot, the trial's draw position divided by R and rounded down, so a later top-up can add groups but never a member to a complete one. A failed member that a persistent grid retry replaced leaves its group to the retry in the same way. Manifest validation re-derives the reduced metric, spread and observed means from the members and requires the snapshot's repeat key, reducer and exactly one member per repeat value. ### Budget and reruns

#### 28. An interrupted trial never consumes the budget; its parameters rerun before any new draw

Budget, progress, completion and status all use the recorded `interrupted` outcome, so `remaining` includes the reruns due. After recording the allocation context and before optimization, the engine creates one Optuna `WAITING` trial for each interrupted trial without a rerun. Its single creation record copies params, distributions and system attributes and tags the source with `phasesweep_rerun_of`. Optuna claims these trials before new draws at any `n_jobs`, and another interruption starts another link in the chain. The same mechanism schedules [persistent grid retries](config.md#search-spaces-and-samplers), whose failed sources still count toward the target.

Shutdown prevents new trainer launches, records its signal as the cause for stopped trainers, and drains parallel workers before reconciliation. An error that Optuna's own cleanup raises over a shutdown, such as the `UnboundLocalError` from its tell, still leaves the phase as that shutdown. Each worker settles its interruption or preserves completed evidence under [invariant 13](#13-no-terminal-trial-without-its-outcome-record). See [interrupted trials](runtime.md#interrupted-trials-rerun) for status and rerun behavior.

#### 30. Managed run status follows the retained attempt outcome

MLflow evidence comes only from the run bound to the attempt. Terminal delivery applies a retained outcome after confirmed cleanup, overriding a conflicting managed-run status from the trainer and leaving trainer-owned statuses alone. A pending persistent trial or a persistent attempt missing from its ledger remains unresolved. An in-memory invocation can end a pending attempt with its own status after cleanup. If it died outright, rebuilding uses the unpublished generation's summary status once the attempt registry entry is retired. `sync-tracking` does not prove trainer cleanup. See [result delivery and recovery](mlflow.md#result-delivery-and-recovery) for the delivery and rebuild rules.

Recovery commits pending intents separately from delivery. Delivery has one core, the one `sync-tracking` runs, and it stops at the first request MLflow does not answer. A run's closeout saves the run's own records, then runs the core for every ended generation and sends the run's own records last, so MLflow never shows a run's result before the outcomes an earlier run left; a confirmed `recover-run` runs it for every generation. The core stages records locally first and makes its first request only when something is pending, after the run's target check or a resolution, which binds no summary run. A run that failed before its target check, a run whose target check got no answer, and a run that is shutting down only save their records for the next run; a shutdown during a pass stops it without a warning, as MLflow was not what failed, and the closing count is logged however the pass ends. Confirmed `recover-run` sets the cleanup marker before persisting run cleanup records or finalizing the snapshot and keeps it until delivery ends. It writes a missing runner status only after delivery. An earlier boot still reads as failed, with cleanup confirmed at the next launch. After mirroring is interrupted, recovery confirms the registered upload workers are gone before finalizing a committed publication's snapshot. See [MCP recovery](mcp.md#run-state-and-recovery) for an unconfirmed worker's effect on recovery.

Target resolution, pending creation searches and delivery workers belong to the invoking generation, or to the run being recovered, so later cleanup is attributed there. A `sync-tracking` worker belongs to the record it is handling. Recovery settles trials in the ledger and saves no MLflow record; delivery rebuilds the missing records of every ended generation it covers from the ledger and lifecycle records, including the summary records of earlier bound, unpublished generations and the recovered run's own. Published generations and existing records keep their own sources. A config whose target is not the recorded one saves nothing and logs a warning. An unreadable or malformed terminal record leaves its outcome unresolved. Target, save or upload failures with confirmed worker cleanup leave work pending for the next run or `sync-tracking` and allow local recovery to succeed.

`tracking.session.resolve_pending_creations` searches for late runs in ended generations after worker cleanup and stops at the first search MLflow does not answer. Only a successful empty search of the original experiment, started after the creation window, can retire an unmatched intent. Earlier misses and failed searches leave it pending. `tracking.publication.delivery_status` counts unresolved creations. The attempt and summary cases are covered by `tests/test_mlflow_terminal_delivery.py::test_managed_creation_before_launch_recovers_the_unlaunched_draw` and `tests/test_mlflow_terminal_delivery.py::test_interrupted_summary_creation_is_reconciled`.

A recovered tracking worker's cleanup receipt commits before its registry entry is retired. Recovery accepts an intact, private receipt from the same generation or for an operation the runner reported as cleanup-uncertain. An unreadable, malformed or misfiled receipt cannot establish cleanup. See [MLflow result delivery and recovery](mlflow.md#result-delivery-and-recovery) for the receipt location and retry procedure.

### Local evidence

#### 32. A trial is scored only from files inside its own attempt directory

PhaseSweep reads a trial's objective, constraints, observations, gate values and digests only from a file that resolves inside that attempt's directory. Config load already refuses absolute, `..`, NUL and empty paths, so a symlink is the only way out, and trials whose links named one shared file would all be scored from whichever trainer wrote it last. A link that stays inside the attempt still reads, and a missing file keeps each reader's own not-found handling. An objective, constraint or gate value outside the attempt fails the trial, live and in recovery, with the refusal as its reason; an observation outside it is omitted with a warning; selection preflight and winner verification refuse a recorded objective source or trainer input that now resolves outside, so selection, publication and resume stop. `required_file` and `artifact_size` on a file or directory read no value and keep following links. The check runs once before each read and is a reproducibility rule, not a security boundary. See [objective evidence](config.md#objective-evidence-constraints-and-gates) for the trainer's side.
