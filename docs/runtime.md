# Runtime behavior

PhaseSweep runs one ordered Experiment on a Linux or macOS host for a trusted researcher or team. It uses same-host file locks and process groups to serialize a persistent experiment and clean up trainer subprocesses. Every process identity records its boot, start time and PID namespace. Linux requires `/proc` to be the procfs of the orchestrator's own PID namespace, with that namespace's PID 1 readable; on hosts using `hidepid`, exempt the operator through its `gid=` option. macOS reads exact microsecond start times through native `libproc`, the boot UUID through `kern.bootsessionuuid`, and records the host PID space as `darwin`. Unreadable identities never authorize a stale-process signal. GPUs are optional; the core CLI can run CPU-only work.

## Output layout

For `workdir: ./runs` and `experiment: demo`, PhaseSweep writes under `runs/demo/` beside the config file:

```text
demo/
  .gitignore
  .ignore
  artifact_root_binding.json
  run.log                         # PhaseSweep's log: every progress line, warning, error and diagnostic message, with timestamps and logger names
  study.journal                   # storage: auto
  generation.yaml
  last_successful_generation.yaml
  attempts/
  generations/
    <generation-id>/
      generation.yaml
      config.snapshot.yaml
      reproducibility.json
      summary.yaml
      phases/<phase>/winner.yaml
  <phase>/
    trials.csv
    trial_00000__<attempt-id>/  # {trial_dir} and PHASESWEEP_TRIAL_DIR, named by the attempt that opened it
      trainer_config.yaml       # yaml_file only
      overrides.json            # json_file only; nested trainer_config with overrides applied
      overrides_resolved.json
      result.json               # when produced by the trainer
    attempts/<attempt-id>/      # one per attempt: PhaseSweep's own records, never the trainer's
      attempt_lifecycle.json
      process_identity.json
      command.txt
      stdout.log
      stderr.log
```

A trial directory holds what the trainer writes and the trial's input. Each attempt's own records sit beside it under `<phase>/attempts/<attempt-id>/`, so a trainer that clears its output directory cannot remove the process identity recovery depends on. `trials.csv` names both: the `attempt_dir` column and `user_attr:phasesweep_trial_dir`.

`last_successful_generation.yaml` points to the immutable generation that represents the latest successful result. Its `generation_id` locates `generations/<generation-id>/summary.yaml` and `generations/<generation-id>/phases/<phase>/winner.yaml`. The summary retains each winner's `observed`, `repeats` and `confound` blocks, plus the recorded top-level `trainer_config` under `override_format: argparse` ([trainer inputs](config.md#trainer-inputs)). Use the [inspection commands](#inspection-commands) to read published or unfinished results.

The root `generation.yaml` names the latest [generation](#timeouts-cleanup-and-continuation) and its `state`: `running`, `published`, `failed` or `publication_failed`. A failed invocation does not replace the last-success pointer. Each generation embeds its carried winners, so reading those records does not require the older generations they cite. Selection and resume verify retained trial evidence.

`trials.csv` is a snapshot of the phase's trials with sampled parameters and user attributes, including [`observe`](config.md#report-only-observations) readings as `user_attr:observed:<name>` and a rerun's source as `user_attr:phasesweep_rerun_of`. It uses the state labels of [`status --trials`](#inspection-commands), and a repeats phase adds `repeat_group` ([repeat groups](#repeat-groups)). Persistent sweeps refresh it periodically during training and at phase exit. Continuation preflight (including a replay) and confirmed [`recover-run`](mcp.md#run-state-and-recovery) refresh it after reconciling recorded trials when the supplied phase matches the study's recorded semantics. This keeps a changed repeat configuration from relabeling recorded trials. With `storage: null`, PhaseSweep writes it at each trial's terminal callback. A winner's `completion` block records the counts checked against the publication. `finished_trials` counts `COMPLETE`, `INFEASIBLE` and `FAIL`. `completed_trials` counts `COMPLETE` alone, as `status` does.

`config.snapshot.yaml` is the executed configuration, including materialized defaults and the resolved invocation context. `reproducibility.json` is the shareable generation identity record. Its `code_revision` is the git commit of the trainer's working directory (`execution.cwd`, or the invocation directory when unset) and whether tracked files differ from it, or `null` outside a git work tree or when git fails. A resume never compares it and a changed commit is not refused; only the [`code_revision` confound check](#confound-verdicts) reads it, to say when ranked trials ran under different revisions. `show-winners` prints the publishing generation's as a `# publication code revision:` line, `unknown` for `null` and with `(dirty)` added when tracked files differed. A winner carried from an earlier generation was produced under that generation's revision, so its `# winner generation:` line adds the source generation's own revision in the same form, or `unreadable` when that generation's record is gone or invalid. Trial directories retain local evidence and attempt lifecycle information used for supported continuation and winner validation.

The generated `trainer_config.yaml` or `overrides.json` holds the trainer base with the effective overrides applied. For these file formats, `overrides_resolved.json` is an overrides-only audit record. For argparse and Hydra, it is the actual flattened input, merging the trainer base with effective overrides before command placeholders expand. Winner observations are empty when none were recorded; `repeats` is `null` outside a repeats phase.

MLflow stores native run bindings in attempt directories, and [delivery and recovery records](mlflow.md#result-delivery-and-recovery) under `tracking/<generation-id>/delivery/` and `tracking/<generation-id>/cleanup-receipts/`.

W&B readers and MLflow workers use disposable scratch under `~/.cache/phasesweep/<backend>/workers/`, or the corresponding `XDG_CACHE_HOME/phasesweep` root; the default home comes from `Path.home()`. Each operation removes its temporary directory. Host locks use a [separate location](#storage-and-locks).

Nothing prunes the trial directories. An interrupted trial's rerun continues in its directory, a retried failure opens a new one, and PhaseSweep never deletes what a trainer wrote, so disk use is roughly the finished trials times the per-trial output, plus the small per-attempt records under `attempts/`. The trainer [owns checkpoint selection](config.md#objective-evidence-constraints-and-gates), so have it bound its own checkpoints, for example by keeping only the last or the best.

### Trust boundary

Logs, evidence, winners, resolved overrides and process identities use ordinary paths and permissions: new files follow umask, and replacements preserve existing modes. Process identity and lifecycle records use atomic replacement; lifecycle replacements have mode `0600`.

Private records inside the tree have these additional requirements:

| Path | Mode | PhaseSweep refuses to |
| --- | --- | --- |
| `generations/<generation-id>/config.snapshot.yaml` | `0600` | replace it unless the existing file is an owner-only regular file with no other hard links |
| `environment.json` in an attempt directory, written only when `execution.record_env` is set | `0600` | replace it under the same condition |
| `attempts/`, the attempt registry | `0700` directory of `0600` entries | read it through a symlink or with shared permissions |

The two files are owner-only while their directories keep ordinary permissions, so only the publishing user can fully validate a published tree: another user is refused as unable to read the publication, which is not corruption, until the publishing user re-reads it or read permission is restored. The same validated, no-follow path handling protects the runtime lock namespace and the MCP `state_dir`.

> [!WARNING]
> `config.snapshot.yaml` is private because it can contain command and environment values. PhaseSweep writes a `.gitignore` containing `*` and a `.ignore` that permits ripgrep searches, without replacing existing files. Keep generated outputs, ledgers, and MCP state out of commits yourself.

## Following a run

`phasesweep run` prints a report on stderr and leaves stdout empty. It opens with a banner naming the config, each phase's trial count, sampler, parallelism and GPU policy, the storage, tracker and workdir, and the absolute path of `run.log`, and it closes with a summary of each phase's trial counts and winner, the files the run wrote and the command that reads the result. In between, every phase start, trial, rerun, skipped phase and winner prints on a line of its own with the time, and so does each warning or error, wrapped to the terminal with every later line under the text after its `warning:` or `error:` label. The last line is `log: <path>`, printed after the summary, after a failure's `fix:` line and after an interrupt's resume hint whenever `run.log` exists. A path wider than the terminal, in the banner and here, breaks after a slash with the rest indented under it. The banner and the summary are printed on the console only. `run.log` holds every progress line, warning, error and diagnostic message with its timestamp and logger name, including what the console leaves out, such as the trainer command of each trial and GPU and storage notes. Optuna logs only errors in both. `run --verbose` records PhaseSweep's debug messages and the traceback of a failure in `run.log` and leaves the console as it is. `run --dry-run` prints no banner or summary, and shows every INFO line of PhaseSweep on the console, such as the GPU pool notes, as the time and the text. A line wider than the terminal wraps at spaces under its first, a path stays whole on a line of its own, and the indented example command is never wrapped, so it can be copied. A shutdown signal prints one line naming it and what it stops, before the resume hint: `Interrupted (SIGINT): stopping 1 trial and waiting for it to exit.` while a trainer runs, or `Interrupted (SIGINT): no trial is running.` when it lands between trials, with any worker still running named after a semicolon, as in `Interrupted (SIGINT): no trial is running; stopping 1 MLflow request.`; the cleanup that follows is confirmed in `run.log` and warns on the console only when it is uncertain. A failure-policy abort appears on the console once, as the error that ends the run (`phasesweep: Phase 'p' aborted: 3 consecutive failed/infeasible trials reached max_consecutive_failures=3. ...`) with its `fix:` line, after the trial line that triggered it. `run.log` also holds a `phase=p ABORTED: 3 consecutive failed/infeasible trials reached max_consecutive_failures=3.` line right after that trial's line. A failure the console already states in a trial's `reason:`, such as a missing objective file, is logged at INFO beside it and so stays out of the console.

The path under each phase's `winner` line is the directory of the winning trial, which holds its trainer config, logs and outputs: one line per trial of a winning repeat group, with their shared parent directory printed once above them, dim on a terminal and broken at slashes to fit it, and absent for a phase the run skipped. A winner whose selection flagged a [confound check](#confound-verdicts) adds a `flagged:` line under its facts that names each flagged check, as in `flagged: survivorship`, with the label yellow on a terminal, and a `details:` line with the `show-winners` command, as typed, that prints the numbers and remedies, so a warning that scrolled away in a long sweep, or that a replayed or skipped phase never printed, stays in view. A run that launches nothing and republishes nothing closes with one sentence instead of the summary, followed by the same `Next:` line: `Finished in 0.1s: nothing to run, 4 trials already finished, and generation <id> already publishes these winners.` The headline counts the trials that count toward each phase's `n_trials`, as the `status --trials` headings do, and a run that resumes a study includes the ones an earlier run recorded, such as `2 phases, 6 trials, 4 from a previous run`. An interrupted trial never counts, so its phase line names it in parentheses after the counts, as in `2 complete (1 interrupted)`, and its rerun counts in its place.

`run.log` is the process-free progress stream. `tail -f <workdir>/<experiment>/run.log` follows a run from any shell, with no MCP server, no lock, and no PhaseSweep process of its own. Successive runs append to the file, so each opens with a line from the engine naming its experiment and process ID, plus its start phase under `--from-phase`, and a run that finishes normally closes with a `Run finished` line carrying the same process ID, the summary headline's counts and its elapsed time, so a start with no finish after it marks a run that failed or was interrupted; neither line reaches the console, and neither carries the command line or any `--set` value. Each report line is one record on the `phasesweep.report` logger, in the order things happen:

The phase start line counts the trials still to run, the parallelism, the trials already finished and the reruns it schedules, the last two only when nonzero. Reruns are [interrupted trials](#interrupted-trials-rerun) and the failed grid cells a raised `n_trials` retries; they are among the trials to run and run before any new draw. A phase with nothing left says `nothing to run` and that it replays its recorded result. Each rerun the run schedules gets a `RERUN` line naming the trial it reruns and the first line of that trial's cause, and the rerun's trial line ends with `rerun of N`; a rerun an earlier run queued but never started counts in the phase start line without a new `RERUN` line.

A trial prints a `RUNNING` line as its trainer starts, once it holds its GPU lease, so a trial still queued for a device prints nothing yet. The line names the devices the trainer sees as `gpu <ids>`, left out when the phase leases none, and the sampled configuration; a rerun that [continues an interrupted trial in its directory](#interrupted-trials-rerun) adds `resumes trial N`.

A trial line gives the trial number, its `state`, the objective under the metric's name, the trial's duration (GPU queue and evidence extraction included), `N/M` and the sampled configuration. `state` reads as in [`status --trials`](#inspection-commands). In `N/M`, `M` is `n_trials` and `N` is the trial's own place in the phase's completion order: the trials counting toward `n_trials` when its outcome was recorded, itself included unless it was interrupted. With `n_jobs` above 1 every finished trial therefore gets a distinct `N`, though the lines may print out of order. `FAIL` and `INFEASIBLE` trials count toward the phase's `max_consecutive_failures`, a `COMPLETE` one resets that count, and an `INTERRUPTED` one leaves it unchanged. The objective is left out when the trial produced none. The configuration excludes the repeat key and shares the line with the trial when the whole line fits the terminal, and otherwise moves to a line under it. A phase with [`repeats`](config.md#repeats) adds `repeat <key>=<value>`, which names the seed or other repeat value that trial ran. The winner line closing each phase gives the winning trial, its objective and its params. In a repeats phase it adds the reducer, repeat count, `sd`, range and member trials, and an accepted partial result adds `INCOMPLETE <finished>/<requested> finished` and the timeout scope.

A trial whose outcome recorded a cause adds `reason:` with its first line, wrapped on the console under the trial with every later line under the text after `reason:`. A trainer that exits nonzero records `non-zero exit code N`. The trial command runs under `/bin/sh -c`, and a shell that does not exec its command survives the command's death and exits with `128 + N`, so a code from 129 to 159 that names a signal records `non-zero exit code 137: the shell's report of a command killed by SIGKILL`; a trainer that exits with such a code on purpose reads the same. A process the kernel kills by signal itself, as when the shell execs the command, records `killed by signal N (NAME)`. For SIGKILL either form adds that the kernel's out-of-memory killer is a common sender, and neither triggers the once-per-phase `execution.inherit_env` hint. Each is followed by `; stderr: ` and the last non-empty line of the trial's `stderr.log` when it has one, so a crash is named without opening the trial directory. The line is read from the last few KiB of the file, stripped of control characters and cut at 200 characters with a trailing `...`. A reason the supervisor records itself replaces that text, such as `timeout after Ns`, or processes the trainer started that are still running 10 seconds after the trainer root exits, which it terminates and, on Linux, identifies by PID and, when readable, the executable name. The same text is the `user_attr:phasesweep_failure_reason` column of `trials.csv` and the `cause` of the trial's recorded outcome. It is whatever the trainer printed, so it stays in these operator-owned records and no MCP tool returns it.

A fatal objective error logs `FATAL OBJECTIVE ERROR` in `run.log` only, skips the trial's line, and ends the run with the error on the console. A trainer interrupted by a shutdown signal under `n_jobs: 1` also skips that line; its next `RERUN` line names the cause.

`phasesweep` exits 0 on success, including an accepted incomplete winner and MLflow uploads left pending after a published result; 2 when the config does not load or the arguments are invalid, including a refused `init` overwrite and an unknown `--from-phase`; 1 when a command is refused or fails, including `sync-tracking` with uploads still pending; 70 on an internal error; and 128 plus the signal number after an [interrupt](#interrupted-trials-rerun). Output to a closed standard stream, a pipe whose reader exited as `| head` does, or a terminal that hung up is discarded and leaves the command's exit status unchanged. Any other write error, such as a full disk, ends the command with `phasesweep: operational error:` and the OS error, and status 1. A refusal or failure that exits 1 ends with a `fix:` line naming the operator step; a config or argument error that exits 2 names what to change in its message. [`mcp call`](mcp.md#calling-a-tool-from-a-shell) has its own exit codes.

## Repeat groups

A phase with [`repeats`](config.md#repeats) ranks complete configurations by the configured reducer over their member metrics. Each member must be COMPLETE, feasible and inside the metric's bounds. Exact ties go to the group with the lowest member [draw position](#interrupted-trials-rerun). The highest member trial number names the group and becomes the winner's `trial_number`; [invariant 27](invariants.md#27-a-repeat-group-is-fixed-once-complete-and-its-last-member-names-it) defines group identity across interruptions and top-ups.

The winner's scalar fields (`trial_number`, `generation_id`, `attempt_id`, `objective_provenance`, `trainer_input`, `constraints`) describe that last member. `metric` is the reduced value, so there is no single winning seed or checkpoint. `show-winners` prints the reducer, spread, repeat key and `repeats.members`, including each member's repeat value, trial number and `trial_dir`. Choose a checkpoint explicitly from those members; the linked full record retains their evidence.

In the full record, `params` and `effective_overrides` omit the repeat key. `repeats` contains `key`, `reduce`, `spread` (`n`, `mean`, sample `sd`, `min`, `max`) and `members`: each member's trial number, repeat value, metric, generation and attempt IDs, objective provenance, trainer input, constraints and observations. Publication validates these against the members and config snapshot; selection and resume verify every member's trial evidence. In `trials.csv`, `repeat_group` is the highest trial number belonging to that configuration so far and can change as members arrive; the `group` column of the `status --trials` member table shows the same number. `status --trials` follows the member table with each group's params, measured/expected count, reducer, eligible aggregate, mean, sample `sd`, range, eligibility and a `winner` mark for the represented winner. Statistics include infeasible measurements, but exclude failed, missing, interrupted and replaced attempts. A partial or ineligible group has no ranked aggregate, and fewer than two measurements have no `sd`. Eligibility uses the current config's bounds; the winner mark identifies the generation named in the header.

The group table also reports each observation's mean as `observed:<name>` and its contributor count as `observed_n:<name>`. Each name counts only completed current members that recorded a finite value for it. For example, two held-out readings in a three-member group have `observed_n:heldout = 2`; the group's objective count remains three. Missing observations do not become zero-valued measurements.

A failed member spends its draw. Seeded random moves on to another configuration slot when its target grows. A [failed grid-cell retry](#retry-fixed-configurations-and-grids) can complete its original group. An `INFEASIBLE` member is never retried, so its group cannot rank. An interrupted member reruns, and a resume also runs the members an interruption never started. A phase cut short by an accepted timeout ranks only the groups it completed. A failure abort ranks nothing until the config [retires it](#timeouts-cleanup-and-continuation). When no group is complete, the phase fails with a `No complete repeat group` error, which counts the incomplete groups and names any metric bound that kept members out.

## Confound verdicts

Each phase's `winner.yaml` carries a `confound` block: advisory verdicts on the population that selection ranked to pick the winner, computed once and frozen at selection time. It never blocks selection or publication and has no YAML switches or threshold settings. The authoritative copy belongs to the published generation; [invariant 26](invariants.md#26-a-confound-verdict-never-joins-a-fingerprint-or-gets-read-as-clean) describes its integrity, fingerprints, top-ups, and inheritance. In a repeats phase the block also lists `ranked_groups`, each complete group's member trial numbers, and its checks compare groups rather than trials.

The block runs four checks, each `ok` (checked, nothing found), `heterogeneous` (checked, found a potential confound, with evidence), or `n/a` (could not be checked - never treat this as clean):

- `evaluation_point`: whether the ranked objectives share a training-progress position. Envelope and W&B objectives use the configured `evaluation_axis`, such as optimizer step or tokens; MLflow objectives use the selected native observation's step. Positions within 1% of the highest count as the same point, and the exact positions are recorded either way. See [W&B evidence](config.md#wb-evidence) for aggregate positions. A phase that searches training length has distinct raw steps by design; see [training-length comparison](config.md#training-length-comparison). `n/a` for an extractor that records no position ([`json` and `log_regex`](config.md#objective-evidence-constraints-and-gates)); for an MLflow objective with `select: min` or `select: max`, whose step is where the best value fell rather than how far the trial trained; when a ranked objective has no recorded position or unreadable provenance; when the ranked objectives declare different axes; or when only one trial was ranked.
- `survivorship`: whether any configuration the phase tried has no result, so the winner was chosen among the rest. A configuration is a trial's params, or a repeat group in a repeats phase, and each one counts once: `ranked` when selection ranked it; `infeasible` when it was measured outside a constraint or the metric's bounds, which never flags, because the experiment's own constraints and bounds define what may win; `failed` when its attempts all failed, evidence-gate and extraction failures included, with nothing measured and no rerun pending; and `untried` when it is a cell of a grid that finished a target covering every cell yet no trial reached it, as when a raised target spends its attempts on failed cells before unvisited ones. A retried grid cell or fixed configuration counts by its latest result, and an interrupted trial through its rerun. `failed_trials` lists the latest failed attempt of each failed configuration. Any failed or untried configuration flags the check; the selection warning names up to five by trial number and params and counts the rest. To retry them, fix the failure and raise `n_trials`: a grid or fixed configuration retries each failed cell once per raise, up to the ceiling [Retry fixed configurations and grids](#retry-fixed-configurations-and-grids) describes, and any other sampler draws new configurations instead. A phase cut short by an accepted timeout leaves configurations that never finished, which its `incomplete` winner reports instead ([`allow_incomplete_on_timeout`](config.md#noisy-objectives-and-small-budgets)). This check always runs.
- `tie`: whether draw order or seed noise could have decided the winner. Without repeats, `ok` only means no other configuration matched the winner's value exactly; it says nothing about the margin. It flags when the draw-position tiebreak chose between trials with different params tied on the exact metric value, rather than between repeats of one configuration. The lowest [draw position](#interrupted-trials-rerun) wins a tie, which outside reruns is the lowest trial number. `n/a` when only one configuration was ranked. `within_noise`, `pooled_sd` and `df` are `null` without repeats. In a repeats phase `tied_trials` names the groups whose reduced value equals the winner's, and `within_noise` (`confound.checks.tie.detail.within_noise` in `winner.yaml`) names the groups whose mean differs from the winner's by at most `t * pooled_sd * sqrt(1/n_winner + 1/n_other)`, exact ties included; either list flags the check. `pooled_sd` is the run-to-run standard deviation pooled over every ranked group, each group's sample variance weighted by its `n - 1`; `df` is the sum of those weights, and `t` the two-sided 5% Student-t value at `df` (4.30 at 2, 2.78 at 4, 2.04 at 30; past 30, `z + (z**3 + z) / (4 * df)` with `z = 1.959964`, within 0.15% of `t` and falling toward `z`), so the threshold can be recomputed from the record. One estimate for the phase borrows strength across configurations, the way a trend across values does, and assumes the noise is about the same size at each configuration; [Noisy objectives and small budgets](config.md#noisy-objectives-and-small-budgets) says what goes wrong when it is not and what extra seeds cost. With `reduce: median` no band is judged, because a median's spread at a few seeds is unknown: the three noise fields are `null`, an exact tie still flags the check, and the check is otherwise `n/a`. Groups are named by their last member, a group with the winner's params is skipped, and the check is `n/a` with one ranked group.
- `code_revision`: whether the ranked trials ran under trainer code that may differ. Each generation records the git commit of the trainer's working directory and whether tracked files differed from it ([output layout](#output-layout)), and `generations` in `winner.yaml` lists each ranked generation's revision beside its ranked trials; in a repeats phase that is every member of every ranked group. One generation is one recorded code state, so ranked trials from a single generation are `ok`, as are generations that all recorded the same clean commit. It flags ranked trials that span generations recording more than one commit, any dirty tree (two dirty trees at one commit may differ, and the record cannot show them equal), or a generation whose revision is `unknown` (not a git work tree, or git failed) or `unreadable` (its record is gone or invalid), unless every ranked generation is `unknown`: with no recorded revision to compare, the check is `n/a` and `generations` still lists them. `n/a` also when only one trial was ranked. The record holds the commit and a dirty flag per generation: edits made while one generation ran, and differences between two dirty trees, are not recorded. A top-up under a changed commit stays allowed; the check only says the winner was chosen among trials that ran under different code, and whether that can move the objective is the reader's call.

Fresh selection logs one `WARNING` per phase: a sentence for each flagged check, led by its name, stating what it found. The run's closing summary names the flagged checks under the winner again, with the `show-winners` command, config path and `--set` overrides included, on a `details:` line. For `evaluation_point` it gives the winner's position and each ranked trial more than 1% short of the furthest. The ordinary causes are a search space that sets training length, a trainer that stops early, and one that reports its best checkpoint. For repeat groups within noise it gives the threshold, the pooled sd behind it with its group count and `df`, and each group's gap, where a gap of 0 is an exact tie; `show-winners` lists the groups' params in `tie_groups`. A separate warning names each searched numeric parameter that [no trial ran beyond the winner on](#retry-fixed-configurations-and-grids). Replays and inheriting phases retain confound verdicts without repeating selection warnings. `show-winners` and the MCP results carry the counts and four remedies: `evaluation_point.remedy`, for a phase that searches training length ([training-length comparison](config.md#training-length-comparison)); `survivorship.remedy`, the retry above, including which phases need new names [if a dependent already has trials](#run-in-stages), or a rerun under `storage: null`; and, for a flagged tie without repeats, `tie.remedy`, which says that draw order chose among identical scores and to compare more distinct values around them ([Noisy objectives and small budgets](config.md#noisy-objectives-and-small-budgets)); and `code_revision.remedy`, which states that the ranked trials may have run under different trainer code.

With [`cost_key`](config.md#repeats), selection advises the cheapest complete feasible configuration within one standard error of the winner's mean (`pooled_sd / sqrt(n_best)`, from the tie check's pooled sd) if it costs less than the winner. The warning names the cheaper configuration's params and the winner's cost, then the gap and the standard error, and says the selected winner is unchanged, as in `cost advisory: epochs=8 is cheaper than the winner's epochs=16, with a mean within one standard error of the winner's (gap 0.005, standard error 0.02); the selected winner is unchanged`; `show-winners` and the MCP results carry the same text. The selected winner, and what later phases inherit, stay unchanged; taking the cheaper configuration is the operator's call. Equal costs prefer the better objective, then trial order. When selection semantics still match, `show-winners` recomputes the advisory from the winner's recorded ranked groups, including after adding `cost_key` to a finished comparison. Groups added by a later failed or unfinished top-up do not join that comparison. See [MCP results](mcp.md#reading-status-responses) for its advisory and confound fields.

## Storage and locks

Only [persistent storage](config.md#experiment-yaml) supports resuming or topping up a study in a later invocation. The journal supports parallel trials on one host. An in-memory run still binds `<workdir>/<experiment>` to in-memory storage. Give that run its own `experiment` or `workdir` before using the same config for persistent work.

When input changes require a fresh study, set a new `experiment` name or, with `storage: auto`, a new `workdir`. Changing only `workdir` leaves an explicit journal's studies in place. The old study stays in its ledger, readable under the config that created it.

When PhaseSweep refuses an older artifact or study format, start with a fresh artifact root and journal. With `storage: auto`, changing the artifact root changes the journal path too. With an explicit journal, choose a fresh path because the format check covers every study in that journal. Use the release or source checkout that wrote older records to read them through PhaseSweep. The raw artifacts (`summary.yaml`, `winner.yaml`, trial logs and journal) remain readable as files.

The selected artifact root and ledger are bound to each other in both directions:

```mermaid
flowchart LR
    root["artifact root<br/>workdir/experiment"]
    ledger["local ledger<br/>journal"]
    root -->|"artifact_root_binding.json names this ledger"| ledger
    ledger -->|"each phase study names this root"| root
    other_ledger["a second ledger"] -.->|"refused: the root names another ledger"| root
    other_root["a second workdir"] -.->|"refused: the studies name another root"| ledger
```

A reused root therefore cannot combine a second ledger's trial counts with the first ledger's publication, and a reused ledger cannot publish into a second tree. Both refusals happen before any trial runs, binding or claim; only the partial-record repair described below can write first.

Runs, `sync-tracking` and confirmed MCP recovery check the tree's binding and ledger format before mutation; a failed check leaves both unchanged. Read-only commands, including `status`, `show-winners`, and `run --dry-run`, never create a missing ledger or directory. If the current user lacks permission to traverse the path to the workdir, these commands report the inaccessible path and advise restoring access. Readers skip an incomplete final journal record. The next `phasesweep run` or confirmed `phasesweep mcp recover-run` repairs it under the same inode lock every PhaseSweep append uses, after saving `<ledger>.<UTC stamp>.bak` beside it with permissions no broader than the journal's. Repair waits at most 30 seconds for an active writer; if it times out, wait for that writer to finish and retry. Kernel locks release when their owning process exits. Damage before the final record is refused as corruption. See [invariant 2](invariants.md#2-validation-writes-nothing) for the repair ordering.

A run, `sync-tracking` or confirmed `recover-run` takes the same-host experiment lock, retrying for at most 0.1 seconds so that a `status` read, which takes the lock for an instant to test it, cannot make it refuse, and is refused with the lock file's path while another process still holds it. The lock covers the artifact root and, with persistent storage, the experiment's ledger studies, so two configs sharing either cannot run at once; an MCP launch for an experiment with a live run is refused as busy before it spawns. Only PhaseSweep writes the live ledger; external Optuna writers do not participate in its lock.

Host locks default to `.cache/phasesweep/locks` beneath the effective user's OS account home, independently of `HOME` and `XDG_CACHE_HOME`. `PHASESWEEP_LOCK_DIR` selects an existing absolute directory; PhaseSweep validates its path, ownership, and permissions without creating or changing it. Provision an owner-only override with `mkdir -p -m 700 /absolute/path`, or use an administrator-owned shared directory with mode `03770` and a group you belong to. On macOS, the root-owned `/var` and `/tmp` aliases resolve to their physical paths before validation; other symlink components are refused. When the OS refuses access to the lock directory or a lock file, as in a sandbox that cannot reach the account home's `.cache`, the refusal names the path and the OS error, and its fix step tells the operator to point `PHASESWEEP_LOCK_DIR` at one existing writable directory shared by every shell, MCP server, and sandbox that launches work on the host, or to run on the host. Separate lock directories bypass coordination, and PhaseSweep never prunes lock files, so do not remove them to clear a permission failure.

### Inspect the ledger with Optuna

The ledger is an ordinary Optuna journal holding one study per phase, named `<experiment>::<phase>`. `phasesweep status <config>` prints its real path, with symlinks resolved, as `ledger_path` (`null` for `storage: null`). Optuna's CLI reads the journal in place without writing to it, so these commands are safe while a sweep runs:

```bash
optuna studies --storage <ledger_path> --storage-class JournalFileBackend
optuna trials --study-name '<experiment>::<phase>' --storage <ledger_path> --storage-class JournalFileBackend
optuna best-trial --study-name '<experiment>::<phase>' --storage <ledger_path> --storage-class JournalFileBackend
```

Copy `ledger_path` exactly: Optuna creates an empty journal at a path that does not exist yet.

For the web dashboard, install `optuna-dashboard` and serve a copy of the ledger:

```bash
pip install optuna-dashboard
cp <ledger_path> /tmp/<experiment>.journal
optuna-dashboard /tmp/<experiment>.journal
```

> [!WARNING]
> Never point `optuna-dashboard` at the ledger itself. The dashboard can rename, delete, and write to studies, and a changed phase study no longer matches the results PhaseSweep published from it. The copy is a snapshot; copy the ledger again to see newer trials.

## Environment variables

No environment variable sets a config key, and the YAML has no `${VAR}` interpolation. PhaseSweep reads these from its own environment:

- The ambient environment is the base of the trainer environment, filtered by `execution.inherit_env` ([trainer contract](config.md#trainer-contract)).
- `CUDA_VISIBLE_DEVICES` takes part in [GPU pool discovery](#gpu-isolation), even when `execution.inherit_env` keeps it from the trainer.
- `PATH` is the base of the trainer's `PATH`, and the controller's own `PATH` finds `nvidia-smi` for GPU discovery and `git` for the generation's code revision.
- `HOME` expands a leading `~` in config paths and sets the default root of the W&B and MLflow workers' scratch. Host locks use the OS account home instead.
- `XDG_CACHE_HOME`, when absolute, moves only that worker scratch to `XDG_CACHE_HOME/phasesweep` ([output layout](#output-layout)). A relative value is ignored.
- `PHASESWEEP_LOCK_DIR` selects the [host-lock directory](#storage-and-locks).
- `PHASESWEEP_HOME` and `XDG_STATE_HOME` affect only the `state_dir` that `phasesweep mcp init-catalog` writes ([MCP setup](mcp_setup.md#2-create-and-review-the-catalog)).

## Trial execution and evidence

Each trial has an attempt-scoped directory and process group. Evidence identifies the generated configuration for YAML, the nested overrides file for JSON, or the resolved overrides and command for Argparse and Hydra. PhaseSweep verifies historical inputs using their recorded format. See [interrupted trials](#interrupted-trials-rerun) for recovery of completed training.

W&B polling starts after successful trainer cleanup and GPU-lease release. It uses the same durable attempt slot and process supervisor, so recovery can find the reader after abrupt parent exit, even if its phase was removed. Uncertain cleanup blocks further work. One absolute polling deadline covers worker startup, SDK construction, requests, retries and summary visibility. Phase or run deadlines can shorten it, and cleanup grace stays separate. The worker reserves the last 2 seconds, or half the time it has left if shorter, for receiving an in-flight answer and reporting the result. When the phase or run deadline capped the polling budget, a polling timeout becomes an [interruption](#timeouts-cleanup-and-continuation) regardless of what the last poll saw. A final lookup that found no run becomes an interruption too. The extractor's own `timeout_seconds` can instead yield a failure or an unreadable tracker, as below.

A finished W&B summary can still gain keys. The first finished read missing a required numeric key starts a 30-second settle window. A finished read with required keys still missing at or after the window fails the trial, including when its reply arrives during the reporting reserve. If W&B gives no answer at the end of the window, polling continues until it answers or the deadline arrives. A missing-key failure or timeout that last read an incomplete summary names the missing and available keys. A gate-only W&B configuration checks the first finished summary and fails on missing keys. Failed, crashed, killed or preempted runs fail the trial.

Once the trial is accepted, a second W&B reader in the same slot locates the objective in run history within a fresh `timeout_seconds` and the remaining phase or run budget. History gets up to 30 seconds to catch up with the summary. Reading it may use the rest of the budget. A failed or timed-out history read records no position and keeps the objective, while uncertain reader cleanup stops the phase.

Accepted remote captures are retained locally, so published results, selection and no-op replay need no SDK, credentials or network reads, even after remote edits or deletion. New remote work checks SDK availability after recognized-state recovery and before accepting a larger target. [W&B evidence](config.md#wb-evidence) and [MLflow metric selection](mlflow.md#select-metrics-and-require-evidence) define the captured values and identities.

[MLflow](mlflow.md#select-metrics-and-require-evidence) captures the selected native observation and its step together after trainer cleanup and GPU release.

A tracker that gives no answer about a finished trial is no verdict on its training. With persistent storage, rejected credentials, a missing SDK, an unreachable or unresponsive server, a reader worker that fails, or a timeout whose last poll got no answer leave the trial `RUNNING` with its training kept and no outcome recorded, unless another failure in the same result is definite. With `storage: null` no later run can read it, so the trial fails with the tracker's reason and the phase goes on. A persistent run starts no further trial and stops with `TrackingTargetUnavailableError` (MCP code `tracking_unavailable`) once its workers drain. Each later run with the same config retries the read before any new work and refuses the same way until the tracker answers, then keeps the result without retraining. A [killed run's](#interrupted-trials-rerun) finished trial waits the same way. A definitive tracker response can still fail the trial if the run is missing, ended unsuccessfully, never finished, or lacks a required key or a valid value. If the tracker is gone for good, a fresh study gives up that training.

W&B reads and every controller MLflow operation, writes included, run the tracker SDK in a supervised worker process instead of the controller. A call blocked in an SDK cannot be cancelled in-process and the SDKs retry on their own, so only a process the supervisor can kill, with its descendants, delivers the one deadline over SDK construction, requests and retries. W&B and MLflow workers run with the composed trainer environment, except that every `PYTHON*` variable is the controller's own and the worker ignores the user site exactly when the controller does, so a worker imports the SDK installation the controller checked for even when the trainer's environment points elsewhere, and the controller's `DO_NOT_TRACK` and `MLFLOW_DISABLE_TELEMETRY` are copied in.

## GPU isolation

By default, `gpu_policy: single_per_trial` leases one device per parallel trial. On Apple silicon macOS, discovery returns one `mps` device without importing a trainer framework. Its `gpu_mps.lock` serializes trials and separate sweeps until the trainer process group exits, without assigning `CUDA_VISIBLE_DEVICES`. The trainer selects its compute device. macOS refuses explicit `gpu_ids` and `gpu_devices`; Intel Macs discover no GPU. `gpu_policy: none` opts out of the lease.

On Linux, discovery uses explicit phase `gpu_ids`/`gpu_devices`, then top-level `env.CUDA_VISIBLE_DEVICES`, then the controller's ambient value, then local inventory. Visibility tokens may be numeric, GPU UUIDs, or MIG tokens. Discovery reads ambient visibility even when `inherit_env` excludes it. The policy rebinds a leased device token, or preserves an empty/`-1` CUDA-disable sentinel, in each trainer. The lease controls visibility and same-host locking, not GPU memory allocation. Leases rotate through the pool: a trial takes the first free device whose host lock it can get, skipping devices another process holds, and a released device rejoins the back of the free list, so no trial is tied to a device. A trial queued for a lease has already drawn its parameters and created its attempt directory. A leased numeric token sets `CUDA_DEVICE_ORDER=PCI_BUS_ID` over any configured or inherited value, while a GPU- or MIG- token keeps a configured or inherited `CUDA_DEVICE_ORDER` and otherwise sets `PCI_BUS_ID`. When `allow_no_gpu_isolation` admits an ambient `CUDA_VISIBLE_DEVICES` whose tokens `nvidia-smi` cannot resolve, trainers get `CUDA_VISIBLE_DEVICES` set to an empty string.

`validate` checks GPU inventory for every phase; `run --dry-run` checks only phases that would launch trials. These read-only checks may invoke `nvidia-smi`, refuse explicit device IDs absent from the local inventory, and warn when workers exceed available devices. They acquire no GPU leases. A sandbox can hide the GPU inventory even when the host has CUDA devices; run GPU validation, dry runs, and training from a host shell with GPU access in that case. Missing-inventory refusals say to fix `nvidia-smi` or rerun from a host shell. For CPU-only work set `gpu_policy: none` and disable CUDA in the trainer environment; `allow_no_gpu_isolation: true` instead runs trials without GPU host locks. With `n_jobs` above 1 and no GPU detected, only `allow_no_gpu_isolation: true` admits the sweep: explicit `gpu_ids` or `gpu_devices` resolve through the same inventory, so an empty one refuses them too. Launch applies the same inventory checks. During a run, a trial blocked by another process's host lock prints one `Waiting for a GPU` report line on the console and in `run.log`, and a trial queued behind this run's own slots logs one `Waiting for GPU lease` line in `run.log` only; retries repeat neither.

`gpu_policy: whole_node` requires `n_jobs: 1` and, on Linux, a unique explicit device list; on macOS it leases the discovered pool. The phase fingerprint records the declared device count as the trainer's world size, so a list whose tokens resolve to fewer distinct GPUs is refused instead of running a smaller world under the same study identity. A MIG token cannot join a multi-device list: CUDA enumerates at most one compute instance per GPU instance, and the MIG inventory does not identify the parent GPU instances. A multi-GPU `torchrun` or `accelerate launch` trainer uses it, and [multi-process and multi-GPU trainers](config.md#multi-process-and-multi-gpu-trainers) says what the launcher and its ranks receive. `gpu_policy: none` disables PhaseSweep's GPU isolation and cannot be combined with an explicit device list; parallel use requires the explicit `allow_no_gpu_isolation: true` acknowledgement.

`gpu_policy: none` assigns no binding. Include ambient visibility in the trainer inheritance contract or set it in `env` if it must be retained.

## Timeouts, cleanup, and continuation

The experiment budget, `timeout_seconds_per_run`, bounds one invocation: its clock starts afresh at every `phasesweep run`, `--from-phase` resume or MCP launch, so it never counts time an earlier invocation spent. It starts once the ledger is claimed, so the experiment lock and ledger setup fall outside it, while stale-attempt recovery and the continuation and evidence checks count against it. Set the per-trial timeout above the longest trial you expect. A phase's `timeout_seconds_per_trial` defaults to 259200 seconds (72 hours), so a hung trial can hold its phase that long unless a phase or run deadline arrives first; an unbounded trial (`null`) needs `allow_unbounded_trials: true`. Its clock covers supervised launch and execution after GPU acquisition, including supervisor startup, but excludes the GPU queue and post-trainer evidence. Phase/run budgets cover those stages too. Cleanup can extend beyond a deadline: once the trainer root exits, everything else it started gets 10 seconds to exit by itself, and anything still running then gets SIGTERM and 10 more seconds before SIGKILL. Unlike phase/run budgets, the per-trial timeout participates in semantic study identity; changing it cannot reuse a populated phase.

On a trial timeout PhaseSweep requests guardian cancellation and records a terminal failed attempt after cleanup. A phase or run deadline that stops a trial in flight records it as [interrupted](#interrupted-trials-rerun) instead. A refused phase timeout ends with a `fix:` line: raise `timeout_seconds_per_phase` and rerun, in the config or in the `--set` assignment that supplied it. Persistent storage resumes the phase and keeps its completed trials; `storage: null` starts over. A run timeout names `timeout_seconds_per_run` instead, including a deadline reached while validating skipped winners for `--from-phase`.

The `max_consecutive_failures` threshold also stops a broken phase. The abort is recorded with the outcome that trips it, so a trial that succeeds afterwards cannot turn the phase back into a result, and a later run stays refused until the config retires the abort. A raised `n_trials` retires any abort. A failure-streak abort is also retired by a `max_consecutive_failures` above the count the abort recorded, but only while `n_trials` still leaves trials to run: the recovery runs exactly those trials, never repeats a completed one, and with none left the limit alone changes nothing. Either way the failure count starts again from zero.

The abort message and subsequent refusals name the key each remedy changes, in the config or through the same `--set` assignments used to run and inspect the study, where an override wins over the file. Recovery keeps recorded results; if a trainer defect invalidated them, change `experiment` to start fresh. A streak of out-of-bounds or constraint-violating trials is identified in the headline; a failed trial directs you to the phase's stderr logs.

When no feasible trial remains at the target, `NoFeasibleTrialError` names the metric bounds and best measured trial. The `status --trials` `reason:` line under each such trial details each violated bound and measured value. Changing a [bound or constraint](config.md#objective-evidence-constraints-and-gates) requires a [fresh persistent study](#storage-and-locks). When all trials crashed in a persistent study, the remedy points at the phase's `trials.csv`, which records why each trial failed or was infeasible, and names the `n_trials` increase. A grid or fixed configuration retries its failed cells, while a random, QMC or TPE phase draws new configurations and never retries a failed one. A fix that changes the study's identity, such as its `metric`, `trial_command`, `trainer_config` or `provenance`, is refused on the next run with its own `fix:` line. A recorded per-trial timeout leads the remedy with the step that fixes it: `timeout_seconds_per_trial` is part of the phase's study identity, so raising it in place is refused as a changed study, and the way through is to raise it and give the phase, and each phase that inherits it, a new `name`, updating every `inherits` to match. The renamed phases start new studies and run again; the others keep their results. A trial whose trainer ran but whose objective the metric extractor could not read gets one sentence of its own, here and in the failure-streak abort's advice: a trainer that wrote the wrong output is fixed and retried at the raised `n_trials`, but a wrong `metric` setting (the extractor's path, key or objective name) is part of the study's identity, so correcting it takes a new `experiment` name. With `storage: null` the sentence names both causes and says to rerun. Run controls such as `n_jobs` can change on a retry.

For a grid or fixed configuration, the remedy names the exact target, for example `raise phases[arm_a].n_trials from 2 to 4 and rerun to retry its 2 failed cells`; COMPLETE and INFEASIBLE cells are not repeated. A grid with unvisited cells adds `and run its N remaining cells`. At the grid's retry ceiling only the limit can help, and while trials remain the remedy gives it instead, for example `raise phases[arm_a].max_consecutive_failures above 2 and rerun to run the 2 trials still left`; if every cell was measured and none is feasible, change the search space or bounds. A sampling phase is told to raise its target, which also runs the trials a streak abort left. With `storage: null` there is no recovery advice because no study persists.

A fatal abort, such as an unexpected objective error, a failed attempt-record write or unconfirmed process cleanup, records no streak, so only a raised `n_trials` retires it and the message states its recorded cause. An unconfirmed-cleanup abort needs cleanup recovery first, which the next run's preflight or `phasesweep mcp recover-run` performs, and a dry run before then says so. A trial the abort stops before its trainer launched is [interrupted](#interrupted-trials-rerun), so the recovery reruns it first. Changing `max_consecutive_failures` governs new work only, apart from retiring a streak abort as above: it never aborts a completed phase retroactively, and a resumed phase whose failure streak already meets the new limit launches nothing until `n_trials` or the limit is raised.

When a timeout and the threshold both stop the same phase short of its target, the timeout decides the outcome: with `allow_incomplete_on_timeout` the phase publishes the winner its completed trials earned, and without it the run stops as a timeout, so a retry with a larger budget does not replay the failure abort. An accepted partial result is a successful run; its winner line says `INCOMPLETE`, gives the finished/requested trial counts and names the timeout scope, and the `completion` block of its `winner.yaml` and MCP results mark it `incomplete`. A later run or `--from-phase` replays an accepted partial target without filling unused slots or rerunning the trials the deadline interrupted, only while the config still sets `allow_incomplete_on_timeout`; its winner line retains that marker, and raising `n_trials` runs those reruns first. `n_trials` counts finished attempts: failed attempts consume the configured target, and interrupted ones do not.

Persistent trial targets cannot decrease, and the refusal names the accepted target to set `n_trials` to at least.

Before a supported continuation, PhaseSweep first checks the artifact-root and ledger binding, then reconciles stale active attempts, and only then verifies recorded trial evidence. `--from-phase` requires earlier published winners for the ancestors of the phases it reaches; an unpublished winner can still be inspected but does not count. When the workdir holds no earlier results at all, the run is refused before it creates the artifact tree, and the message says to run without `--from-phase` so the earlier phases run first; a mistyped `--set workdir=...` is the usual cause, so check the path before dropping the flag. Earlier published winners are carried after their evidence checks, even when unrelated to the reached phases, and keep their original source provenance. An independent arm can therefore start after an earlier arm aborted, without a winner for that unrelated arm. The run still stops when a phase fails; starting another arm is an explicit resume. [Sampler rules](config.md#search-spaces-and-samplers) govern new draws and failed grid-cell retries when `n_trials` rises, and [fixed-configuration rules](config.md#phase-composition) govern retries without a search space. A launch and the dry run refuse an invalid larger target before any phase runs.

A run writes a generation when it launches a trial or publishes winners that differ from the current publication. A refusal before the first trial, or a replay matching the existing publication, leaves `generation.yaml` and `last_successful_generation.yaml` unchanged; a replay with changed winners or no publication publishes a new generation. Before a claim, failure performs no post-failure study reconciliation and MCP reports stage `preflight` ([status responses](mcp.md#reading-status-responses)). After trials launch, an interrupted or failed generation retains its inspection record without advancing the last-success pointer. Signals are absorbed across the final publication commit.

### Resolve a changed study or trainer environment

A phase's study stores the inputs used to calculate its fingerprint. When a later config disagrees, the refusal lists up to ten changed dotted paths with their old and new values, truncates long values and counts the rest; a study without those stored inputs reports the two fingerprints instead. A change to a phase's own keys can be rerun by renaming that phase and the phases inheriting it, as the `fix:` line says; any other change needs a [fresh study](#storage-and-locks). If `execution.cwd` was unset and the trainer working directory changed, the refusal gives the fix. A winner file records only the hash, so a skipped phase whose winner no longer matches reports the two hashes.

Each trial records the tracked trainer environment as plain text in `phasesweep_trainer_env` and its SHA-256 in `phasesweep_trainer_env_digest`. A mismatch names the recorded and current value of each variable that differs; for a search-path list, a name ending in `PATH`, it lists only the entries present on just one side, or says the same entries changed order. A reused winner's environment warning prints the difference the same way. Follow the fix line to run with the recorded values and unset the variables it names. A different shell, server or sandbox can change `PATH`, `LANG`, `LC_ALL` or `TZ`. See the [trainer contract](config.md#trainer-contract) for what gets tracked and how to configure it before a fresh study.

### Run in stages

1. With persistent storage, run a config containing just the first stage's phases. Read the winners with `phasesweep show-winners`.
2. Append the later phases to the same file and leave the finished phases as they are. Keep the same `experiment`, `workdir`, storage and [trainer working directory](config.md#trainer-contract).
3. Preview the extended config with `phasesweep run CONFIG --dry-run` before running it. The finished phases replay their published winners without launching trials, and the appended phases inherit the recorded values.

A run refuses to top up a finished phase while a dependent study already holds trials, because those studies are bound to the phase's published winner. A changed config or trainer environment of a reached phase is refused before this, by the run and its dry run alike, so the top-up refusal comes only for a phase that keeps its trials. The refusal's `fix:` line gives the way through: give each phase that inherits the enlarged phase, directly or indirectly, a new `name` and update their `inherits` references. The enlarged phase keeps its finished trials and runs the rest, and the renamed phases start new studies and run again. To reuse independent phases while changing one phase's own settings, rename that phase and all phases that inherit it, directly or indirectly, and update their `inherits` references. The other phases replay. If you change shared settings such as the trainer command, metric or provenance, [start a fresh study](#storage-and-locks). `--from-phase NAME` selects where to start. To stop at a planned stage, include only those phases in the config.

### Retry fixed configurations and grids

A [fixed configuration](config.md#phase-composition), with no `search_space` or `repeats`, keeps at most one COMPLETE or INFEASIBLE result. After a failed attempt, raise `n_trials` by one to retry: one failure permits `n_trials: 2`. A retry runs under the same `timeout_seconds_per_trial`, a phase key that cannot change once the phase has trials, so after a timeout raise it and give the phase, and each phase that inherits it, a new `name`, updating every `inherits` to match, instead. A higher target is refused, as is any increase after a measured result. Interrupted attempts rerun without spending the target. With in-memory storage, `n_trials` above 1 is refused at load because nothing can be retried. With persistent storage, config loading accepts a higher target because recorded failures could justify it, and `validate`, `run` and its dry run check it against the recorded attempts, so a fresh fixed configuration with `n_trials: 2` is refused by all three. Use [repeats](config.md#repeats) to measure the configuration several times.

A persistent grid retries failed cells when `n_trials` rises beyond its matrix size, one extra attempt per failed cell per raise within the target. A retry that fails waits for the next raise; COMPLETE and INFEASIBLE cells never repeat. For a two-cell grid with two failures, `n_trials: 3` retries one and `n_trials: 4` retries both. A partial-grid target up to the matrix size keeps exploring unvisited cells. `validate` checks an above-matrix target, like a fixed configuration's raised target, against the recorded attempts with the same ceiling as `run` and its dry run, counting a RUNNING attempt whose outcome records a failure as finished, as recovery settles it. One whose completed trainer evidence awaits recovery counts as a failure too, the verdict that allows the most retries, because `validate` recovers nothing: it refuses only a target that `run` refuses whatever that evidence turns out to hold, and `run` enforces the real ceiling once it has recovered it. An oversized target on a fresh grid is refused before launch.

Fresh selection warns, whatever the sampler, when the winner's value of a searched numeric parameter is the lowest or highest of at least three distinct values the phase's finished trials tried: no trial ran beyond it, so the best value is not located on that side. Int and float ranges, log or linear, count, and so do numeric categorical choices, ordered by value; boolean, mixed and string choices and the repeat axis do not. A FAIL or INFEASIBLE trial beyond the winner counts as tried, so a diverged run above the best learning rate silences that side; an interrupted trial tried nothing. One warning names every such parameter with the values tried and says whether the winner is on the configured bound. On the bound, only a wider range reaches past it, and `search_space` is part of the phase's study identity, so widen it and give the phase, and each phase that inherits it, a new `name` as [Run in stages](#run-in-stages) describes. Where the configured range extends past the winner, raising `n_trials` draws more values in the same range and keeps the finished trials. A continuous float range reaches its bound only with a draw equal to it, so its warning names the range's end even when the optimum lies past it; if more trials keep the winner at the edge, widen the range. In simulated random sweeps over three parameters with an interior optimum and noise a fifth of the objective's rise across half the range, it fired in about a quarter of 8-trial sweeps, a few percent at 16 trials and almost never at 32, so in a sparse sweep it reports coverage rather than a fault. Silence does not show the optimum is inside the range: any worse trial beyond the winner, noise included, silences that side, and with the optimum on the bound, 32-trial simulated sweeps fired roughly one time in five under random sampling and under one in ten under TPE, whose draws cluster near it. The warning is not stored and does not repeat on replay; `show-winners` and MCP results recompute it from the ledger as `edge_advisory` over the finished trials the phase held at selection, with `edge_advisory_status` `available`, `not_at_edge`, or `unavailable` when those trials or the producing config cannot be read. Cells left without a result, failed or never tried, are reported by the [`survivorship` check](#confound-verdicts).

### Interrupted trials rerun

An interrupt of `phasesweep run` is not a trial timeout. On SIGINT (Ctrl-C), SIGTERM or SIGHUP, PhaseSweep asks each active guardian to cancel its supervised process group and exits with status 128 plus the signal number: 130 for Ctrl-C, 143 for SIGTERM. A closed terminal or a dropped SSH session sends SIGHUP, which stops the run like Ctrl-C and costs the trial in flight; a run started under `nohup` ignores the hangup and keeps going, and tmux, screen or a service manager protect a long sweep as well. A stopped run ends by saying what to do next, then printing the command to paste on a line of its own, quoted like the `Next:` command of a finished run's summary and carrying every `--set` and the `--from-phase` you passed: `phasesweep: stopped. Rerun the same command to resume.` for persistent storage, which keeps the finished trials and reruns the interrupted ones first, or `phasesweep: stopped. Rerun the same command to start over: storage: null keeps no completed trials between runs.` for `storage: null`. The `log:` path follows. A dry run prints no such line, and a run whose published result was already committed prints `phasesweep: stopped after the result was published.` instead. A trainer stopped in flight records the outcome `interrupted` with a cause that names the signal as the interrupt line does, such as `orchestrator interrupted by SIGINT`, and becomes `FAIL` in the ledger. Once the signal arrives no trainer starts: a trial still waiting for a GPU slot or about to launch records `interrupted` with the same cause, and under `n_jobs` above 1 the run waits for the workers' bookkeeping before reconciliation. A phase or run deadline that stops a trainer in flight records `interrupted` too, with the deadline as its cause, and so does a phase abort that stops a queued trial before its trainer launched.

Shutdown, timeout and supervised-abort requests for known trainer groups go through their live guardian. It saves the lifecycle state `terminating` before signalling the trainer, with `ended_by: cancelled`, or `ended_by: timed_out` for a per-trial timeout, which the controller requests with SIGUSR1 instead of SIGTERM. That ending remains authoritative even if the trainer handles SIGTERM by exiting zero. The final record says how every attempt ended: `trainer` with its return code when the root exited by itself, including a kill PhaseSweep did not send, such as the OOM killer's; `not_started` when the launch failed before the trainer's `execve`; `guardian_lost` when the guardian died without a verdict. The guardian reaps an exited trainer root while confirming group cleanup, including when procfs is unavailable. Cleanup is confirmed only once nothing the trainer started can still run. On Linux that includes processes that left the trainer's process group, such as the ranks torchrun starts in sessions of their own: the guardian adopts them when their parent dies, holds the GPU lease while they run, and signals each one's own group, with a rank adopted only after its launcher was killed getting SIGKILL at once. Also on Linux, a process whose main thread ended while its other threads keep running, as a C or C++ trainer can leave, reads as a zombie in procfs but counts as running, and is signalled, until its last thread exits ([invariant 10](invariants.md#10-lifecycle-states-that-skip-signalling-are-written-only-on-proof)). Once the trainer root has exited, cancellation no longer applies: the guardian still waits out the 10-second helper settle and gives its verdict, so a Ctrl-C at that moment keeps the result of a trainer that exited 0 and left nothing to terminate, which the next run extracts without retraining under persistent storage. A trainer that had failed, by a nonzero exit, a signal PhaseSweep did not send or by leaving a process the guardian terminates, keeps its own failure and reason, such as `non-zero exit code 1; stderr: ...`, and counts toward `max_consecutive_failures`; only a trainer the shutdown itself stopped is recorded `interrupted`. Shutdown waits for that verdict, which takes about 20 seconds when a leftover child ignores SIGTERM, and allows it 25 seconds before it reports cleanup as uncertain. If the guardian has exited or dies during cleanup, PhaseSweep cleans the trainer group directly within the existing cleanup allowance; the affected trial follows the phase's failure policy. Only that group can be cleaned then: a process that left it, such as a torchrun rank, re-parents to init once the guardian is gone and is no longer tracked. If the guardian cannot save cancellation intent, it leaves the trainer running and retains its GPU leases; cleanup remains unconfirmed while that group lives.

After a hard kill, the trial stays `RUNNING` until recovery. Recovery verifies the surviving guardian's recorded process identity, checks that the owning ledger can be read, asks the guardian to settle the attempt and waits for its exit status and cleanup record before starting another trial. A trainer that already exited successfully keeps its result while the guardian waits for its helpers. A trainer that is still running is cancelled by its guardian. If the guardian is already gone, direct trainer-group cleanup requires a verified group and a durable interruption in the owning ledger before signalling. The trial's trainer return code and duration are saved before a tracker worker reuses the process slot, and recovery uses those values if the worker was interrupted. A kill while a trainer or worker is starting, before its process identity is written, leaves a launch that no process received, and recovery settles it without signalling ([invariant 10](invariants.md#10-lifecycle-states-that-skip-signalling-are-written-only-on-proof)): a trainer that had finished keeps its result, and one that never started reruns. If shutdown defers extraction after completed training, the trial stays `RUNNING` with its attempt registered. For persistent storage the warning says the next run extracts the result without retraining. With `storage: null` it says the result is lost. A shutdown that lands after the trial's outcome was recorded, before Optuna committed it, prints no such warning: the stopped run commits the trial as it exits and prints its trial line, noted `recovered`. Every trial recovery settles prints that line: a kept result as `COMPLETE`, a trainer that crashed before its run stopped as `FAIL` with its `reason:`. Recovery polls once per pass when [tracker evidence is pending](#trial-execution-and-evidence). Nothing relaunches a stopped sweep by itself: after a killed runner or a reboot, run the same command again, or under MCP launch the experiment again once the dead run is [settled](mcp.md#run-state-and-recovery). With persistent storage that run recovers the stale attempt first and reruns its trial before any new draw.

If a measurement was recorded, recovery verifies the frozen capture or original file and completes the trial with that value. Restore missing or changed file evidence before resuming. If the evidence cannot be restored, use a [fresh experiment](#storage-and-locks). A recorded rejection settles as `FAIL` even if its diagnostic was never written. With confirmed trainer success and no recorded outcome, recovery extracts evidence under the producing config and records the same outcome a live trial would, including a measured infeasibility or a tracker rejection. A trainer that ended by itself with a failure before its run died, by a nonzero exit, a kill PhaseSweep did not send or its per-trial timeout, keeps that failure with its stderr line and counts toward the producing phase's `max_consecutive_failures`, so a configuration that crashes every time aborts the phase instead of rerunning forever. Otherwise recovery preserves a recorded failure or fatal outcome, or records an interruption: for a trainer PhaseSweep stopped, one that never started, or one whose ending nobody recorded, such as after a reboot. A result file alone never proves a successful exit.

Successful settlement logs `Confirmed process cleanup for RUNNING trial ...` at INFO, including after an intentional interrupt. The trial's recorded cause distinguishes signal shutdown from stale-run recovery.

An interrupted trial reads `INTERRUPTED` in `status --trials`, `trials.csv` and `run.log`. It never counts toward `n_trials` or the `max_consecutive_failures` streak, and selection, its confound checks and repeat groups pass over it. The next run that reaches its phase adds one trial with the interrupted trial's parameters, logs a `RERUN` line for it, and runs every rerun before any new draw. A rerun is an ordinary trial with its own number and attempt, and its `rerun_of` names the trial it reran; a rerun that is interrupted in turn gets a rerun of its own. A phase whose partial result was [accepted at a deadline](#timeouts-cleanup-and-continuation) replays it without rerunning until `n_trials` is raised, and on `storage: null` nothing reruns, because the study ends with the process.

A rerun continues where the interrupted attempt stopped. It runs the same command in the same trial directory, with the same `{trial_dir}`, `{trial_id}` and `{run_name}`, so a trainer that resumes from the latest checkpoint in its output directory picks up from there; PhaseSweep sets no resume flag and copies nothing. Only `PHASESWEEP_ATTEMPT_ID` is new, and the new attempt's captured streams and records go under `attempts/<attempt-id>/`. The rerun is scored only from value files its own attempt wrote: a result, constraint or observation file left unchanged since before it launched fails the trial as not written by this attempt, so a trainer that resumes must write its result again on every run. The rerun starts only once the stopped attempt's process group is confirmed gone, so two processes never write one directory. A failed grid cell or fixed configuration that a raised `n_trials` retries runs from scratch in a directory of its own.

Every trial has a draw position. A trial that is not a rerun takes the next one, 0, 1, 2 and so on, and a rerun takes its source's. Samplers draw by position rather than trial number, so an interruption never repeats or skips a draw; a discrete space can still yield the same configuration twice. Grid and seeded random reproduce an uninterrupted run at any `n_jobs`; seeded TPE and CMA-ES do at `n_jobs: 1`, given the same trial values. [Invariant 29](invariants.md#29-a-seeded-phase-draws-by-position-so-an-interruption-never-repeats-or-skips-a-draw) gives the position contract. Grid shuffles with a fixed seed when none is set, so it reproduces unseeded too. `validate` and the dry run print this per phase as `(resumable, reproducible)` or `(resumable)`; on `storage: null`, where nothing resumes, they print `(reproducible, not resumable: in-memory storage)` or `(not resumable: in-memory storage)`.

## Inspection commands

Use `validate`, `run --dry-run`, `status` and `show-winners` to inspect an experiment without launching work. `validate` reads existing studies only to check [raised fixed or grid targets](#retry-fixed-configurations-and-grids), and never compares the config with a study's recorded identity, so an edit that study refuses, such as a changed search space or `timeout_seconds_per_trial`, passes `validate` and is refused by the dry run. `validate` and `run --dry-run` print the same contract facts, each wrapped to the terminal: the metric and each `observe` entry give their extractor as its kind followed by `key=value` fields, a value holding a space quoted. A passing `validate` says so in a closing sentence wrapped to the terminal, `Checked the config alone. A dry run also compares it with the recorded study and its trials' environment, and checks the trial program on PATH:`, followed by the `phasesweep run CONFIG --dry-run` command as typed on a line of its own, unbroken so it can be pasted. The dry run captures the journal once without writing and reports each phase's `finished`, `remaining` and [rerun](#interrupted-trials-rerun) counts. A met target or accepted partial target replays its recorded winner, so children preview with real inherited values. Otherwise their sample commands use stand-ins. `DRY RUN example command` names those keys and the parent that must publish, as in `(placeholders until 'architecture' publishes a winner: model.name)`. Keys the child fixes itself are real values.

Pass the same `--set` assignments used for `run` to each inspection command so it resolves the same study; see [run-time overrides](config.md#run-time-overrides) for the syntax and config-relative path rules. `validate` and `run --dry-run` print the resolved `artifact root:` alongside the trainer working directory. `status` and `show-winners` refuse a missing or empty study directory and name the path they checked.

After the phase lines, `DRY RUN total: would launch 30 trials (2 reruns) across 3 phases (2 other phases replay)` sums new work, including reruns, and counts replaying phases separately. Phases skipped by `--from-phase` are omitted. If another operation holds the experiment lock or the lock cannot be checked, the preview marks the counts as a hypothetical restart from the captured snapshot. The next launch's counts depend on which trials finish. A refused preview prints no total.

For readable, settled studies, the dry run applies the run's checks and messages before previewing phases:

- Publication access, integrity and retained phase-history boundaries, on every storage backend.
- Study direction and failure-policy state, accepted targets, [retry ceilings](#retry-fixed-configurations-and-grids), and top-ups that would invalidate bound descendants.
- [Abort recovery](#timeouts-cleanup-and-continuation), accepted partial results and a feasible winner on replay.

Several refused studies produce one combined refusal. Before any phase previews, as before a run launches anything, each reached study's own config is compared with the one it recorded, and each reached phase that would launch trials gets the launch preflight a run applies before it allocates any: the [environment cohort](config.md#trainer-contract) of its recorded trials, RUNNING ones included, the trainer's working directory, and the [trial program](config.md#trainer-contract) on the trainer's `PATH`. Inherited values are compared once known; placeholders defer that comparison until the parent has a result.

An unreadable ledger produces a warning and fresh-phase previews; a real run refuses it. A RUNNING attempt whose successful trainer completion awaits extraction reads `EVIDENCE_PENDING` in recovery predictions. The dry run refuses to guess its trial and rerun counts and asks for a normal resume to recover the evidence first. Other RUNNING attempts are counted as recovery would settle them: failed when their outcome records failure or fatal error, otherwise interrupted and owed a rerun. Such phases get only the fixed/grid attempt-limit check, without failed-cell retries or accepted-target, abort and partial-decision checks until recovery; the warning names this limitation. The dry run does not recover attempts or re-prove replayed trial evidence. `validate` checks the trainer's working directory and a trial program written with a `/`, but leaves a program found through `PATH` to the dry run and the launch, since the `PATH` that counts is the one the run starts with. `--from-phase` validates published ancestors and their evidence; unfinished winners remain inspectable, and a normal resume can reuse their completed trials. Inspection reads only current-format local experiments.

`status CONFIG` prints trial counts and publication identity as YAML: `workdir`, [`ledger_path`](#inspect-the-ledger-with-optuna), `current_generation_id` (the generation the root `generation.yaml` names), `published_generation_id` (the validated publication, or `null`), `represented_generation_id` (the latest claimed generation, falling back to the publication), `is_published`, and `publication_integrity`, which is `ok`, `absent`, `failed` or `permission_denied`, with `publication_error` beside the last two. Each phase entry starts with its `name`, then `trials` counts `COMPLETE`, `INFEASIBLE`, `FAIL`, `INTERRUPTED`, `RUNNING` and `WAITING`, listing only states that occur. `COMPLETE` counts feasible measured trials; infeasible measurements spend `n_trials` like failures. `generation_trials` counts trials owned by the represented generation. Each phase also gives `n_trials`, `trial_data_available`, `published_study_unavailable` and `winner`, the chosen winner path or `null`. `winner_generation_id` identifies that winner's producing generation, `winner_is_published` says whether it belongs to the validated publication, and `winner_config_matches_current` reports semantic agreement with the loaded config (`null` when unknown). These labels belong to each phase: a later unfinished generation can contribute a new winner for one phase while another retains its published winner. Top-level `is_published` describes the represented generation, rather than every chosen winner's source. A phase whose recorded abort or failure streak would refuse a run gets two comment lines before the YAML, whether or not a run is active: the diagnosis `run` prints, then its `# fix:` step. Otherwise, when the experiment lock is idle and a winner is retained unpublished, `status` prints a `# Winner retained but not published` comment, naming the missing feasible winner when one blocks publication, and a `# fix:` comment line beneath it with that phase's remedy or a rerun instruction that distinguishes persistent resume from an in-memory restart. All of these stay comments, so the output remains one YAML document. Trials recorded RUNNING while no PhaseSweep operation holds the experiment lock were left by a run that stopped before recording them: one killed without cleanup, or one that ended with a finished trial whose tracker gave no answer. `status` and `status --trials` first print one comment line for them, which says that a rerun of the same config settles them and that a trainer still running is stopped and its trial rerun, so waiting for it to exit keeps its result. Both commands omit this guidance while a run is active or the lock cannot be probed. The trial data and publication verdict remain readable when the probe fails. Each call probes the lock at most once. An MLflow experiment adds its pending and delivered [upload](mlflow.md#result-delivery-and-recovery) counts.

`status CONFIG --trials` prints the experiment name, one line naming the generation the winner marks come from, and one aligned plain-text table per phase instead, for reading; `trials.csv` is the machine-readable table. The generation line reads `published generation ID` or `unpublished generation ID`; when the phases' winners come from different generations it says so and each phase heading gets a `winner from generation ID (published)` line, and without a publication it says no winner is marked. Finished phases can be marked while later phases run. A phase heading reads `depth: 2 of 2 trials, eval_loss (lower is better)`: the first number is how many trials count toward the phase's `n_trials` and the second is the configured target, so a phase still short of it reads `depth: 1 of 2 trials`. Rows that do not count follow in parentheses, by state in lower case and in the order waiting, running, interrupted, as in `lr: 1 of 6 trials (1 running, 1 interrupted), eval_loss (lower is better)`; an interrupted trial never counts but its rerun does, so a finished phase that holds a rerun reads `2 of 2 trials (1 interrupted)`. The heading ends with the objective and its direction from the metric the study recorded, which its trial values were measured under; when the config's `metric.name` or `metric.goal` has since changed, a note under the heading names the config's and says a run refuses the study. A phase whose recorded abort or failure streak would refuse a run prints that diagnosis and a `fix:` line under its heading, worded as `run` words them. The columns, left to right, are a leading column holding the word `winner` on the trials the represented winner stands on (the one trial, or every member of the winning repeat group), `trial`, the objective under the metric's name, one column per swept parameter in config order with the repeat key last (then any other key a trial recorded, `-` where a trial lacks it), `group` for a [`repeats`](config.md#repeats) phase, one `observed:<name>` column per [`observe`](config.md#report-only-observations) name any trial recorded, `state`, `time`, and `rerun of` once the phase holds a [rerun](#interrupted-trials-rerun), which names the trial it reran. Rows sort by the parameter columns from left to right: a categorical parameter by its place in the configured choices (a value outside them after the listed ones), a numeric one by value, a missing value last, and ties by trial number, so the winner is not necessarily first. A trial's recorded failure, interruption or infeasibility cause prints as a `reason:` line under its row. Under the rows, a `winner trial N directory:` line names the directory of each winning trial, one per member of a winning repeat group, relative to the working directory and on a line of its own, never wrapped, when it is too wide for the terminal; a phase with no winner, or a winning trial that recorded no directory, has none. A [`repeats`](config.md#repeats) phase follows its rows with one [summary per repeat group](#repeat-groups) under the same marker, parameter columns and sort. `state` is the Optuna state, except that a COMPLETE trial that violated a constraint or the metric's `min`/`max` bounds reads `INFEASIBLE` and an interrupted trial reads `INTERRUPTED`. The table is for reading, so it prints the objective and observed values to six significant digits, float params to four significant digits (a float of 10000 or more prints in full, never in exponent form) and `time` to one decimal place with an `s`; `trials.csv` and `winner.yaml` hold the exact values. `time` is the trainer's wall-clock runtime, which ends when the trainer command's root process exits, without the helper settle after it, or once a timed-out or interrupted trainer is stopped, and it reads `-` for a trial that never ran one; the duration on a trial's line in the [run report](#following-a-run) spans the whole trial, GPU queue and evidence extraction included. Tables print at their natural width and are never reflowed; only prose, such as a `reason:` line, a note under a heading and the comment about RUNNING trials, wraps to the terminal width (`COLUMNS`, then the terminal's own size, then 80 columns). On a terminal the winner row is bold with the word `winner` in green; nothing is styled when output is redirected or `NO_COLOR` is set, even to an empty value. With `storage: null` there is no ledger to read, so each phase's heading says so and, once a run has written one, points at the `trials.csv` of its last run. A table prints even when the publication is corrupt or unreadable, followed by the same error and exit status as plain `status`. For plots and the dashboard, point Optuna's own tools at the ledger as described in [Inspect the ledger with Optuna](#inspect-the-ledger-with-optuna).

`show-winners CONFIG` reads each phase's usable winner from the latest claimed generation, falling back to its validated published winner when that generation has none. It does not search older unpublished generations. Each winner names its generation and whether it is published. Both published and unpublished results keep their producing metric, phase plan, annotations and `trainer_config` base; semantic config drift is marked historical. Config-agreement labels compare the producing phase plan with the corresponding prefix of the loaded configuration: appended pending phases preserve agreement, while changes to producing phases or metric semantics do not. Each phase prints its comment, objective, params, effective overrides, completion flags, observations, repeat spread and confound summary, or `(no winner yet)`. `tie_groups` lists the repeat configurations within the [tie check's noise band](#confound-verdicts) with their params, gap, pooled standard error of the difference and threshold; with `reduce: median` it lists the groups whose median equals the winner's, at gap 0 with the standard error and threshold null. A null `tie_groups` means the retained trial details are unavailable. `cost_advisory_status` distinguishes `not_configured`, `unavailable`, `no_cheaper_configuration` and `available`, so a null advisory is interpretable. `edge_advisory` names each searched parameter [no trial ran beyond](#retry-fixed-configurations-and-grids), and `edge_advisory_status` says whether it was checked. `show-winners` prints floats to twelve significant digits. Retained records, `trials.csv`, `winner.yaml` and MCP numeric results keep their stored values. Repeats winners include their repeat key, member values and trial directories for checkpoint selection. The `# full record:` path contains the retained evidence. A corrupt or inaccessible publication makes the command fail without printing winners. Producing snapshots must match the SHA-256 in their generation's `reproducibility.json`; missing, unreadable, invalid or mismatched evidence refuses inspection and recovery with artifact-repair guidance.

For the packaged starter, the learning-rate winner contains this result (abridged; trial numbers depend on grid order):

```yaml
trial_number: 0
metric:
  eval_loss: 0.3
params:
  optimizer.lr: 0.0003
effective_overrides:
  model.n_layers: 8
  optimizer.lr: 0.0003
```

`params` contains what this phase sampled; `effective_overrides` also contains inherited and fixed values applied to the trainer's base configuration. See [repeat groups](#repeat-groups) for member checkpoint selection and the [output layout](#output-layout) for result files.
